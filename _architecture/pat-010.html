Pattern catalog / PAT-010

We build with CMS core and first-class modules. A contributed module or outside library gets in only if it passes an admission test, because we must patch it ourselves forever.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: Secure by design, Extensible, not headless, Accessible by default
  • Main layer: Architecture and platform

Supports: Only a small, vetted set of modules and libraries is allowed in.

  • Dependencies and delivery
  • Security and isolation
  • Accessible experience and plain language

Found by the Solution Architect in the solution architecture (Solution Architecture section 5.9, the Interactive Content paper (section 8, admission path) and). Not named by the EA. Offered as a candidate pattern, pending EA confirmation.

The rule

DO

Try CMS core, then a first-class module, before anything else. Admit a contributed module or library only through the admission path, with a named patch owner and an SBOM entry.

DON'T

Add a module or library because it saves a week. On a network where nothing refreshes itself, each one is a permanent patch duty and a new source of flaws.

When this comes up

  • Every feature request has a module that does most of it. The first week is cheap. The next five years are not.
  • The isolated network never refreshes itself (After go-live, development is on the high side). Each addition is a licence, an SBOM entry, a flaw stream and a patch duty.
  • Playback uses Video.js is the precedent: one mature library surfaced three transitive licences that had to be resolved.

What pulls in different directions:

  • Speed now, against cost for years.
  • Rich features, against a small attack surface.

Picture it

The experience

A requester brings a need. They should see quickly whether core already meets it, and if not, what the review needs and how long it takes.

WhoWhat they needWhat goes wrong without the pattern
Requester (Communications)A clear answer and a reason.A silent wait, or a flat no.

Security AuthorityEvidence in one place.Evidence scattered across emails.
Content editorsFeatures that look and behave alike.Many widgets with different keyboard behaviour.

Design rules for this pattern

  • Ask for the need, not the module.
  • Show the core option that was tried.
  • Use the same checks every time.
  • Give a reason with every answer.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Can a requester see why a request is waiting?
  • Does the form refuse a request that has not tried core?
  • Does every admitted item have an owner, a version and an SBOM entry?
  • Does the reference component work by keyboard, in English and French?
  • Is the yearly review run and recorded?
How it works
  1. State the need. A named content need, in plain words, that core and first-class modules cannot meet.
  2. Try core first. Content Moderation, Workflows, Views, Media and Layout Builder do a great deal. Prove they fall short before going further.
  3. Vet the candidate. Licence, transitive dependencies and SBOM, flaw scan, no outside calls, and accessibility of its output. This is the bar Playback uses Video.js set.
  4. Name the patch owner. A role (the unassigned platform administration role is relevant here) agrees to patch it for the life of the system.
  5. Build a reference component. An accessible, bilingual example is built before anyone writes content with it.
  6. Register and pin. Add it to the registry with regression tests. Host it on the internal mirror at one pinned version. Ship it as a signed artefact.
  7. Review each year. Does it still earn its place? A module with no users is removed.
  8. Say no kindly. A request that fails goes back with the reason and the core option.
Definition cards

Hover or focus any dotted term in this page to see the same definition.

Admission path

The steps a new module or library must pass before it is allowed in: a named need, vetting, a reference component, and registration.

Why it matters hereEach admitted item is a permanent patch duty. The path makes it earn that cost.

SBOM (software bill of materials)

A list of every component inside a piece of software, with versions and licences.

Why it matters hereWithout it we cannot say what to patch when a flaw is announced, and nothing refreshes itself here.

Signed artefact

A built package, such as a container image, with a digital signature that proves who built it and that it has not been changed.

Why it matters hereOn the isolated network nothing can fetch or check a file for itself. The signature is how we know a file is the one we built.

Isolated network

A network with no connection to the internet. Nothing can be downloaded at install or run time.

Why it matters hereEvery tool, package, font and asset must already be inside. A pattern that needs an outside service is not allowed.

Service blueprint

A picture of a service in layers: what the person sees, and what staff and systems do out of sight to make it happen. A line of visibility separates the two.

Why it matters hereMost intranet failures happen behind the line, such as a stale index or a missed review. The blueprint puts an owner on each one.

Wireframe

A plain sketch of a screen that shows what goes where. It leaves out final colours, wording and branding on purpose.

Why it matters herePeople can agree on layout, language switch and reading order before anything is built, and a vendor can show the same screen back.

Trade-offs

What we gain

  • A small, known set of dependencies.
  • Faster response when a flaw is announced.
  • Fewer surprises in accreditation.
  • A visible reason for each exception.

What it costs

  • Slower to add features.
  • Some needs are met with plain code that we then maintain.
  • Vetting takes expert time.
  • People may feel the answer is always no.

When not to use it

  • The change is configuration of core only. No review is needed.
  • A flaw fix to an admitted item. Use the normal patch route, as a signed artefact.
Checks every pattern must pass

Bilingual (official languages law)

A reference component must work in English and French, including strings and right-sized layouts, before it is admitted. A module with English-only text is not admitted without translations we can review.

Accessible (WCAG 2.1 AA)

Its output must meet WCAG 2.1 AA and use design system components where one exists. Vetting includes testing with a keyboard and a screen reader.

On-premises, no outside connection

No runtime call to the internet. It comes from the internal mirror at a pinned version. Updates arrive only as signed artefacts.

FLAG On-premises conflict

A module or library that fetches fonts, scripts, telemetry or updates from an outside address is rejected at vetting.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Can you list every contributed module and library in your design, with its reason and patch owner?
  • For each, can you show why core or a first-class module was not enough?
  • Is there an SBOM, and are all licences identified?
  • Does any item make a call to an outside address at run time?
  • Are items pinned to a version on the internal mirror?
  • Does each item come with an accessible, bilingual reference component and tests?

Proposed decision record

Every added dependency passes the admission path

A contributed module or third-party library is added only through the admission path, with a named patch owner, an SBOM entry and a pinned version on the internal mirror. Core and first-class modules are tried first.
