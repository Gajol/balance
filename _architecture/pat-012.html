Pattern catalog / PAT-012

Anything that crosses into the isolated network crosses as a signed, scanned package from a known build. It never arrives as a download or a hand copy.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P5, P3
  • Main layer: Architecture and platform

Supports: Everything entering the isolated network is built, signed and verified first.

  • Dependencies and delivery
  • Security and isolation

Found by the Solution Architect in the solution architecture (which sets a signed-artefact pipeline into the isolated network). Not named by the EA. Offered as a candidate pattern, pending EA confirmation.

The rule

DO

Build and sign the signed artefact on the low side, carry it across by the Security-owned transfer, and check the signature on the high side before anything runs.

DON'T

Copy files, pull packages or download updates straight into the isolated network. Nothing there can tell a good file from a bad one, and nothing there refreshes itself.

When this comes up

  • The isolated side has no internet and no automatic updates. Everything it runs must be brought in.
  • Many things must cross: code, container images, scanner signatures, models, taxonomy files, mirrored packages.
  • A quick hand copy is tempting during an outage. It bypasses the only check the network has.

What pulls in different directions:

  • Speed in a hurry, against a trusted chain.
  • Fewer steps, against proof of where a file came from.

Picture it

The experience

The people who feel this pattern are the release manager and the Security Authority. They need to see, at a glance, what is crossing, whether it is verified, and where it runs.

WhoWhat they needWhat goes wrong without the pattern
Release manager (IT)One status page showing each step and its result.Guessing which build is running.
Security AuthorityEvidence of origin, scan and approval.A file they cannot vouch for.
Content ownerTo know when a change will go live.A silent delay.

Design rules for this pattern

  • Show each step's result in words.
  • A failed check stops the release and says why.
  • Say when a change will reach staff.
  • Ship both languages together.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Can a release manager see every step, its result and its owner on one page?
  • Does a bad signature stop the release on the high side?
  • Does the same artefact run in staging and production?
  • Do English and French strings ship in the same release?
  • Is the staff notice clear, dated and in both languages?
How it works
  1. List what crosses. Code, container images, scanner signatures, models, taxonomy files and mirrored packages are all artefacts. If it is not on the list, it does not cross.
  2. Build once on the low side. The pipeline builds from version control. The image is the unit of deployment (Container-based production environment).
  3. Scan and write the SBOM. Run the checks and record every component in an SBOM.
  4. Sign it. The build signs the artefact. The signing key is held by the pipeline, not by a person.
  5. Hand to Security. A Security-owned procedure carries the artefact across (DevOps pipeline moving signed artefacts across the boundary). The transfer is one way and logged.
  6. Verify first. The high-side pipeline checks the signature and the SBOM before any install. A failed check stops the line.
  7. Prove on staging. The same artefact goes to staging with real data and real integrations, then to production (Development and staging on the isolated side).
  8. Keep the record. For each artefact: who built it, who approved the transfer, when it was verified and where it runs.
Definition cards

Hover or focus any dotted term in this page to see the same definition.

Signed artefact

A built package, such as a container image, with a digital signature that proves who built it and that it has not been changed.

Why it matters hereOn the isolated network nothing can fetch or check a file for itself. The signature is how we know a file is the one we built.

SBOM (software bill of materials)

A list of every component inside a piece of software, with versions and licences.

Why it matters hereWithout it we cannot say what to patch when a flaw is announced, and nothing refreshes itself here.

Isolated network

A network with no connection to the internet. Nothing can be downloaded at install or run time.

Why it matters hereEvery tool, package, font and asset must already be inside. A pattern that needs an outside service is not allowed.

Shared taxonomy

One controlled list of terms (topics, divisions, content types) kept in both official languages and applied to content.

Why it matters hereThe same terms drive CMS pages, search facets and analytics reports. It is what lets us ask 'which HR pages are stale, and who owns them?'

Service blueprint

A picture of a service in layers: what the person sees, and what staff and systems do out of sight to make it happen. A line of visibility separates the two.

Why it matters hereMost intranet failures happen behind the line, such as a stale index or a missed review. The blueprint puts an owner on each one.

Wireframe

A plain sketch of a screen that shows what goes where. It leaves out final colours, wording and branding on purpose.

Why it matters herePeople can agree on layout, language switch and reading order before anything is built, and a vendor can show the same screen back.

Trade-offs

What we gain

  • Proof of where every file came from.
  • One path in, one record of it.
  • The same artefact runs in staging and production.
  • A failed check stops a bad release early.

What it costs

  • Slower than a hand copy, even in an outage.
  • The signing key and the transfer need careful ownership.
  • Scanner signatures and models need a regular delivery schedule.
  • A long gap between releases means older software.

When not to use it

  • Data created inside the isolated network. It stays inside, and has its own backup rules.
  • Content the department publishes out of the isolated network. Use the separate one-way feed out.
Checks every pattern must pass

Bilingual (official languages law)

Both language versions of content and strings ship in the same artefact, so one language cannot lag the other after a release. A release is checked for parity before it crosses.

Accessible (WCAG 2.1 AA)

The build runs the automated accessibility tests before signing, so a release that fails WCAG 2.1 AA checks never crosses (P1).

On-premises, no outside connection

This pattern is how the isolated network stays closed. No runtime fetch, no refresh from the internet. Only signed artefacts, through one transfer.

FLAG On-premises conflict

Any plan that has the high side download updates, packages or signatures from the internet is a conflict. Refresh must arrive as a signed artefact through the transfer.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Can you show an artefact, its signature and its SBOM?
  • Does the high-side pipeline refuse an artefact with a bad or missing signature?
  • Is the same artefact used in development, staging and production?
  • Does any step on the high side reach the internet?
  • How do scanner signatures and taxonomy files arrive?
  • Can you show the record of who built, approved and deployed one artefact?

Proposed decision record

Everything that enters the isolated network is a signed artefact

Code, images, scanner signatures, models and taxonomy files cross into the isolated network only as signed artefacts through the Security-owned transfer. DevOps pipeline moving signed artefacts across the boundary sets this for code and images. This record would extend it to every kind of file.

Status: Proposed, pending EA confirmation. Not yet logged.
