Pattern catalog / PAT-013

Accessibility is tested automatically at three points: when we build, when someone publishes, and on the live site every week. People test the rest. Nothing relies on one audit at the end.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: Accessible by default, Bilingual parity, Automated
  • Main layer: Content and governance

Supports: Accessibility is checked at the build, at publishing and on the live site, with proof for audit.

  • Accessibility assurance
  • Accessible experience and plain language
  • Bilingual parity
  • Measurement and analytics

Requested by the EA (add accessibility under Content and governance, with checks in the build pipeline and at publishing). Drafted by the Solution Architect from the Accessible by default principle. Pending EA confirmation.

The rule

DO

Run an accessibility gate at the build, at publishing and on the live site, in English and French. Keep the results as evidence and give every finding an owner.

DON'T

Rely on one audit before go-live, or on a tool alone. Never remove live content because a tool complained. A person decides.

When this comes up

  • WCAG 2.1 AA is a pass or fail rule (Accessible by default). A page that fails is a barrier for some employees and a finding at audit.
  • Problems arrive from two sources: code (templates, theme, components) and content (images, headings, links, documents, video). A check on only one of them misses half.
  • Content changes every day. A site that passed at go-live can fail next month, and French pages can fail in ways English pages do not.
  • Automatic tools find only part of the problems. The rest needs people, including people who use assistive technology.

What pulls in different directions:

  • Strict gates, against authors who need to publish.
  • Automatic speed, against human judgment.
  • One shared standard, against two languages with different text lengths.

Picture it

The experience

An author is told about a problem while writing, in plain words, and fixes it before publishing. The designer and the content manager see one view of what is failing, in each language.

Design rules for this pattern

  • Say what is wrong, where, and how to fix it, in plain words.
  • Separate errors that hold from advice that guides.
  • Never use colour alone to show a problem.
  • Show the same help in English and French.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Does a missing alt text hold a draft with a plain message?
  • Does a failed build test stop a release from being signed?
  • Do English and French pages show their own results?
  • Can a keyboard user reach every advice note?
  • Can a finding be traced to an owner and a due date?
How it works
  1. Set the standard. WCAG 2.1 AA is the pass or fail line. CAN/ASC-EN 301 549 is the stated target. Both are tested in English and French.
  2. Use first-class parts. Build on design system components without overriding their markup, and on first-class modules. Fewer custom parts means fewer new failures.
  3. Gate 1, the build. Every change to code runs axe-core through a test runner on a fixed set of pages, in both languages and at phone and desktop widths. A failure stops the build. No artefact is signed (DevOps pipeline moving signed artefacts across the boundary, PAT-012).
  4. Make the build set realistic. The test pages cover every content type and component, with long French text and 200% zoom, so layout failures show before release.
  5. Gate 2, authoring. The editor shows problems as the author writes. Machine-certain errors hold the draft: missing alt text, empty links or headings, skipped heading levels, video with no caption file. Judgment items, such as link wording, only advise.
  6. Hold, never remove. A gate may stop a draft from going live. It never takes live content down. A finding on live content is a flag (PAT-009) to the owner of record.
  7. Gate 3, the live site. A scheduled crawl runs inside the network against live English and French pages and files. It reports per language (PAT-011) into the content health report.
  8. Test with people. Before go-live and each release, staff test with NVDA, JAWS and keyboard only. Employees who use assistive technology test real tasks. Every page has an accessibility feedback link that joins the same log.
  9. Keep the evidence. One log holds each gap, its owner, a fix date and the release that closed it. It is reviewed each release. This is the audit evidence and the base of the conformance report.
  10. Waivers are short. A known issue may be waived only with a named owner, a reason and an end date. An expired waiver fails the gate again.
Definition cards

Hover or focus any dotted term in this page to see the same definition.

WCAG 2.1 AA

The Web Content Accessibility Guidelines, level AA. The government pass or fail standard for web accessibility.

Why it matters hereIt is the line a page or a release must not fall below. Automatic tools can test part of it. People must test the rest.

Accessibility gate

A check that must pass before something moves on: a release before it is signed, or a page before it is published.

Why it matters hereA gate turns accessibility from a hope at the end into a rule at every step.

axe-core

A free, open-source engine that tests a web page for common accessibility failures and explains each one. Pa11y and Playwright can run it.

Why it matters hereIt runs inside our network and has a French message set, so reports can be read in both languages.

Assistive technology

Software or devices some people use to read or operate a computer, such as a screen reader, voice control or a magnifier.

Why it matters hereReal users with assistive technology find problems that no automatic tool can see.

Conformance report

A written statement of how a product meets each clause of a standard, with the gaps and the plan to close them.

Why it matters hereIt is the evidence an auditor asks for. EN 301 549 and the federal accessibility law both lean on it.

First-class modules

Modules that ship inside CMS core and are built, tested, secured and released by the CMS core team, on the same schedule as core. Examples: Language, Content Translation, Workflows, Content Moderation and Media. Contributed and custom modules are not first-class.

Why it matters hereA first-class module is patched when core is patched and needs no extra vetting. Everything else is a permanent patch duty for us, so it must pass the admission path first (PAT-010). The RFP asks vendors to use first-class modules wherever they can.

Content health report

A scheduled report that joins CMS metadata (owner, review date, language) with analytics traffic to show what is stale, unowned or unread.

Why it matters hereIt is the evidence that content is owned and being refreshed or disposed of, per language.

Signed artefact

A built package, such as a container image, with a digital signature that proves who built it and that it has not been changed.

Why it matters hereOn the isolated network nothing can fetch or check a file for itself. The signature is how we know a file is the one we built.

Service blueprint

A picture of a service in layers: what the person sees, and what staff and systems do out of sight to make it happen. A line of visibility separates the two.

Why it matters hereMost intranet failures happen behind the line, such as a stale index or a missed review. The blueprint puts an owner on each one.

Wireframe

A plain sketch of a screen that shows what goes where. It leaves out final colours, wording and branding on purpose.

Why it matters herePeople can agree on layout, language switch and reading order before anything is built, and a vendor can show the same screen back.

Trade-offs

What we gain

  • Problems are found when they are cheap to fix.
  • Releases cannot make accessibility worse without someone choosing it.
  • Evidence for audit builds up as work goes on.
  • French and English are proven equal, with numbers.
  • Authors learn from advice while they write.

What it costs

  • Automatic tools find only part of the problems. People are still needed.
  • Gates can slow an urgent release or a publish.
  • False alarms need tuning, and a noisy gate gets ignored.
  • Each tool outside core is a patch duty.
  • Someone must triage the findings each week.

When not to use it

  • A throwaway draft that never leaves the author's workspace.
  • A third-party tool the department cannot change. Record the gap in the log and plan the fix instead.
Checks every pattern must pass

Bilingual (official languages law)

Every gate runs on English and French pages and reports each language separately. French is tested for its own failures: language tags, longer text, reflow at 200% zoom. Neither language is the default.

Accessible (WCAG 2.1 AA)

This pattern is the proof. Its own screens meet WCAG 2.1 AA. Findings are written in words with the rule name, not only a colour or a score.

On-premises, no outside connection

Every tool runs inside the network from internal mirrors. Nothing calls an outside scanner or a hosted checker. Tools arrive as signed artefacts (PAT-012).

FLAG On-premises conflict

Hosted checkers (for example browser extensions that send pages to a vendor, or online scanners) are not allowed. Use self-hosted tools only.


FLAG On-premises conflict

A tool that loads scripts from a CDN at run time fails the constraint. Bundle everything inside the artefact.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Show a build that fails because an accessibility test failed, and show that no artefact was signed.
  • Do the build tests run on English and French pages, at phone and desktop width?
  • Show a draft held for missing alt text, and a video held for a missing caption file.
  • Does a gate ever remove live content on its own?
  • Show a scheduled crawl of live pages with results per language, with no outside connection.
  • Which parts of the checks need a person, and who does them?
  • Can you produce the findings log and conformance report for any release?
  • List every accessibility tool you propose, where it comes from, and its licence.

Proposed decision record

Accessibility is checked at the build, at publishing and on the live site

No release is signed unless the automatic accessibility gate passes in English and French. Drafts with machine-certain errors cannot be published. Live pages are scanned on a schedule and results are reported per language. People test with assistive technology before go-live and each release.
