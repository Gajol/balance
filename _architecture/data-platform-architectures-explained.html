These four names are often presented as rivals. They are not. Each answers a different question, and most real platforms use more than one.

Short answer for a product owner

  • Data lake: where the data is kept. Cheap storage for any kind of data.
  • Lakehouse: a lake with proper tables on top, so you can trust, update and query it.
  • Medallion: a way to organize data in layers, from raw to ready to use. A pattern, not a product.
  • Data fabric: a layer that connects and governs data across many platforms. It points at the data. It does not hold it.

"Fabric" here means the architecture idea, data fabric. It is not the same thing as any one vendor's product that happens to use the word.

How they fit together

1. Data lake

A data lake is a large store where data lands in its original form: files, extracts, logs, documents, images. You decide the structure when you read it, not when you save it.

Problems it solves

  • Data sits in many silos and formats. The lake gives it one place to land.
  • Storage in a warehouse is costly. Lake storage is cheap.
  • You do not yet know how the data will be used. The lake lets you keep it first and decide later.
  • Data science and AI need raw, varied data, not only neat tables.

Problems it creates

  • Without a catalog and owners, it turns into a "data swamp". Nobody can find or trust anything.
  • Files are hard to update or delete. This matters for privacy and correction requests.
  • No transactions. Two jobs can leave the data half-changed.
  • Weak access control if it is not designed in.

2. Lakehouse

A lakehouse keeps the lake's cheap storage and open files, then adds a table layer on top. The table layer gives the lake the good habits of a database: safe updates, rules on structure, and one place for reports and AI to read from.

Problems it solves

  • Two copies of the data: one in a lake for AI, one in a warehouse for reports. A lakehouse aims for one copy.
  • Safe updates and deletes (transactions), so jobs do not corrupt each other's data.
  • Bad data arriving silently. The table enforces its structure.
  • "What did this look like last month?" Tables keep history (time travel).
  • Lock-in. Open table formats let several tools read the same data.

Problems it creates

  • More moving parts: storage, table format, catalog, engine. Someone must run them.
  • Tables need regular housekeeping (small-file clean-up, old version removal).
  • Table formats compete. Pick one and check which tools support it.
  • Overkill if the data is small and neat. A normal database may be enough.

3. Medallion

Medallion is a design pattern for the inside of a platform. Data moves through three layers. Each layer is cleaner and more useful than the last. The names are Bronze, Silver and Gold. The pattern is usually built on a lakehouse, but it also works in a warehouse.

LayerWhat is in itWho uses it
BronzeData as received from the source. Kept unchanged, with load date and source. This is your audit copy.Data engineers. Anyone who must prove what arrived.
SilverCleaned, de-duplicated, standardized and matched across sources. One agreed version of each business thing, such as a client or a case.Analysts and data scientists.
GoldShaped for a specific use: a report, a dashboard, a measure, an AI feature. Business names and rules applied.Business users and leaders.

Problems it solves

  • Nobody agrees which number is right. Gold has one agreed version.
  • Raw and cleaned data are mixed together. Layers keep them apart.
  • "Where did this figure come from?" You can trace Gold back to Silver and Bronze.
  • A source changes or a rule was wrong. Rebuild Silver and Gold from Bronze.
  • Clear places to put quality checks and access rules.

Problems it creates

  • More copies of the data, and more storage and processing.
  • Delay. Each layer adds time before data is ready.
  • It can become ceremony. Three layers will not fix poor ownership or unclear rules.
  • Gold tables can multiply with no one owning them.
Open sourceCommercial
It is a pattern, so you build it with tools: dbt for transformations; Apache Airflow or Dagster to schedule; Great Expectations or Soda for quality checks; Apache Spark or Trino to run it Databricks (which popularized the term), Snowflake, and Microsoft Fabric offer built-in pipeline and quality features; Informatica and Talend (Qlik) for data integration

4. Data fabric

Data fabric is the connecting layer. Large organizations have data in many platforms, sites and clouds. A fabric uses metadata (data about the data) to find it, describe it, track where it came from, and apply the same access rules everywhere. Where it makes sense, it lets you query data where it sits instead of copying it.

Problems it solves

  • "Does this data exist, and who owns it?" A shared catalog answers.
  • Every team builds its own copy. A fabric lets you reuse data in place.
  • Different access rules in every system. A fabric applies policy once.
  • Impact and audit questions: lineage shows what feeds what.
  • Mergers, reorganizations and multi-site data. Connect without a big move.

Problems it creates

  • It is only as good as its metadata. Poor descriptions mean poor results.
  • Querying live across systems can be slow, and it puts load on source systems.
  • It is not a box you buy. It is a set of capabilities plus an operating model.
  • Needs clear data owners. Data mesh is the usual ownership model to pair with it.
  • Vendor claims vary a lot. Ask what it actually does.

If your problem is...Ask for...

Our data is small, neat and mostly reportsA regular database or warehouse. You may need none of these four.

What to watch in a federal setting

  • Where the data lives. Data residency and security categorization decide whether you can use a public cloud, a sovereign cloud or on-premises. Check this before you choose tools.
  • Open formats. Parquet and an open table format keep your exit options open. That matters over a long system life.
  • Privacy and records. You must be able to find, correct and delete personal information, and keep records for the right time. Lakehouse tables help. Plain lakes do not.
  • Audit trail. Bronze plus lineage lets you show where a figure came from.
  • Skills and run cost. These platforms need people to run them. Count that cost, not only licences.
  • Start small. Pick one business domain and one use. Prove it, then grow. A fabric over a mess is still a mess.

Plain-word glossary

Words you will hear in meetings
Object storageLow-cost storage that holds files at very large scale. The base of a data lake.
Open table formatA public standard for how tables are kept in files. It adds safe updates and history. Iceberg, Delta Lake and Hudi are examples.
Transaction (ACID)A change that fully happens or does not happen at all. No half-done updates.
Time travelThe ability to see a table as it was at an earlier point.
CatalogThe directory of what data exists, what it means and who owns it.
MetadataData about data: names, descriptions, owners, formats, tags.
LineageThe trail showing where data came from and what it feeds.
Federation or virtualizationQuerying data where it sits, instead of copying it first.
Data meshAn operating model where each business domain owns and shares its data as a product. Often paired with a data fabric.
Data warehouseA database built for reports on neat, structured data. The older cousin of the lakehouse.
