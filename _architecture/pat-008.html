Pattern catalog / PAT-008

When a supplier may change, we write one small CMS plugin that talks to it, behind an interface we own. The rest of the intranet never learns the supplier's name.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: Extensible, not headless, Secure by design
  • Main layer: Architecture and platform

Supports: A supplier can change without staff noticing and without a rewrite.

  • Integration with other systems
  • Dependencies and delivery

Found by the Solution Architect in the solution architecture (one small custom module replaces a third-party library). Not named by the EA. Offered as a candidate pattern, pending EA confirmation.

The rule

DO

Name the capability in business words, define a small plugin interface for it, and put each supplier behind a CMS plugin that meets it.

DON'T

Call the supplier's interface from templates and modules, or add a large library for one operation. Changing supplier then means a rewrite, and the library is a patch duty for good.

When this comes up

  • Several integrations may change supplier: calendar availability, captions, the records system, the identity provider.
  • Every library or direct call we add is a permanent patch obligation on a network that never refreshes itself.
  • Calendar availability from the internal mail system is the worked example: one operation was needed, so one small module was built without a library.

What pulls in different directions:

  • Fast delivery now, against a rewrite later.
  • A flexible interface, against a plain one that is easy to test.

Picture it

The experience

Staff should never notice a supplier change. The page looks the same before and after. The experience this pattern protects is no change at all.

Design rules for this pattern

  • The screen must not change when the supplier does.
  • Show only values from the interface.
  • Test a swap on staging before production.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Do the before and after screens match, in English and in French?
  • Is the reading order the same for a screen reader?
  • Does a switch to a stub supplier change nothing a person can see?
  • Does a failing supplier leave a blank badge and a working page?
How it works
  1. Name the capability. In business words: "get availability", "store a record", "make a caption". Not the supplier's verbs.
  2. Write the interface. Define the inputs, the outputs, the errors, the limits and what "nothing" looks like. Keep it as small as the need.
  3. Build one plugin per supplier. Use CMS's own plugin system. The plugin holds all supplier detail: addresses, field names, quirks.
  4. Choose by configuration. Which plugin is active is a setting in version control, not code in a page.
  5. Keep libraries out unless admitted. If a library is needed, it goes through PAT-010 first. Prefer a few lines of our own code for one operation.
  6. Fail quiet. An error from the supplier returns "nothing" to the caller, never an exception on a page.
  7. Test the contract. A stub supplier proves the interface. Each real plugin must pass the same tests.
  8. Record the choice. The decision record names the capability, the plugin and why no library was used.
Definition cards

Hover or focus any dotted term in this page to see the same definition.

Plugin interface

A short written contract in code that says what a capability takes in and gives back. Each supplier is a separate plugin that meets it.

Why it matters hereChanging supplier means writing one new plugin. Nothing else in the intranet changes.

Isolated network

A network with no connection to the internet. Nothing can be downloaded at install or run time.

Why it matters hereEvery tool, package, font and asset must already be inside. A pattern that needs an outside service is not allowed.

Service blueprint

A picture of a service in layers: what the person sees, and what staff and systems do out of sight to make it happen. A line of visibility separates the two.

Why it matters hereMost intranet failures happen behind the line, such as a stale index or a missed review. The blueprint puts an owner on each one.

Wireframe

A plain sketch of a screen that shows what goes where. It leaves out final colours, wording and branding on purpose.

Why it matters herePeople can agree on layout, language switch and reading order before anything is built, and a vendor can show the same screen back.

Trade-offs

What we gain

  • Changing supplier is a contained change.
  • No large library for a small need.
  • A clear contract that vendors can be tested against.
  • Fewer patch obligations.

What it costs

  • A little more design work at the start.
  • A wrong interface is hard to change once many callers use it.
  • We own the plugin code and its tests.
  • Risk of building an interface for a supplier change that never comes.

When not to use it

  • There will clearly only ever be one supplier and one caller. A plain module is enough.
  • The need is large and the library is mature. Take it through the admission path (PAT-010) instead.
Checks every pattern must pass

Bilingual (official languages law)

The interface returns values from a fixed set or identifiers, never supplier text, so wording is always ours and translated. Contract tests run once per language where output is shown.

Accessible (WCAG 2.1 AA)

The interface says nothing about presentation, so accessible rendering stays in one place. Anything shown to a person follows PAT-007 and the design system components.

On-premises, no outside connection

Each plugin must reach only internal systems. A supplier that needs an outside route is rejected at design time. Plugins and their configuration ship in the signed release.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Can you show the interface and say, in one sentence, what capability it gives?
  • Can you switch to a stub supplier by configuration alone, with no code change in callers?
  • Does an error from the supplier show as "nothing" and never break a page?
  • Do the contract tests pass for every plugin?
  • Is any third-party library used, and was it admitted through the path?
  • Does the interface return values from a fixed set, never supplier text?
