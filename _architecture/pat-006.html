Pattern catalog / PAT-006

Some data changes by the minute and lives in another system. A background worker keeps a small cache fresh, and the page only reads the cache. The page never waits on the other system.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P3, P5, P6
  • Main layer: Architecture and platform

Supports: Minute-by-minute values such as availability appear without slowing any page.

  • People and live status
  • Performance and caching
  • Integration with other systems

Named by the EA on 2026-10-24 using calendar availability as the example. Lifted from Calendar availability from the internal mail system. The wider rule is the Solution Architect's proposal.

The rule

DO

Let a queue worker fetch the data in batches and write it to a short-lived cache. The page reads the cache through a placeholder, and shows nothing if the cache is empty.

DON'T

Call the other system while the page is being built. One slow or throttled system then slows every page, and a failure shows up as a broken page.

When this comes up

  • Calendar availability sits beside people's names. It changes by the minute and differs for each person shown.
  • The source is a shared system, the internal mail system, with its own limits on how often it may be asked.
  • The intranet caches pages by language and role. Personal, live values must not break that.

What pulls in different directions:

  • Fresh values, against a source that throttles requests.
  • A fast, shared page cache, against values that differ per person.
  • Showing something useful, against showing nothing when the source is down.

Picture it

The experience

A person looking at a colleague's page wants to know, right now, whether that colleague is free. The page must open fast whether or not the answer is available, and it must never show a guess as a fact.

Design rules for this pattern

  • Show a word and its age. Never show only a colour.
  • Show nothing, not an error, when there is no value.
  • Show only a coarse status, never meeting details.
  • Use the same fixed set of words, translated by us, in both languages.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Does the page open at normal speed with the calendar system switched off?
  • Is an empty status shown as blank, with the rest of the card unchanged?
  • Does every status show a word and its age, and read correctly in a screen reader?
  • Are the English and French words the same set, with the same meaning?
  • Does a test meeting title ever appear on the page or in the index?

How it works

  1. Mark the value as live. Name the data, who may see it, and how old it may be before it is dropped.
  2. Ask in batches, off the page. A queue worker asks the source for many items at once, on a schedule, within the source's limits.
  3. Write value and age. The live-value cache stores the value with a short life. It can be served a little stale while a refresh is queued.
  4. Read through a placeholder. The page leaves a lazy placeholder where the value goes. It reads the cache only.
  5. Fail quiet. If the cache is empty or the source is down, the value is blank and the page renders as normal.
  6. Keep it out of the shared cache and analytics. The value never enters the page cache, search or analytics.
  7. Show it as words. Use a fixed set of values, translated by us (see PAT-007), never colour alone.
  8. Measure. Report cache hit rate, value age and refresh failures per language.

Definition cards

Hover or focus any dotted term in this page to see the same definition.

Queue worker

A background program that takes jobs from a list and does them one batch at a time, away from any page a person is waiting on.

Why it matters hereIt is the only thing that calls the source, so the source's limits are respected in one place.

Live-value cache

A small store for values that change by the minute. Each entry has a short life and an age, and may be served slightly stale while it refreshes.

Why it matters hereKeeps minute-by-minute values out of the shared page cache, so one personal value cannot make every page uncacheable.

Lazy placeholder

A gap CMS leaves in a cached page and fills in afterwards for each viewer.

Why it matters hereHow a personal value appears on a page that is otherwise shared by everyone in a role.

A picture of a service in layers: what the person sees, and what staff and systems do out of sight to make it happen. A line of visibility separates the two.

Why it matters hereMost intranet failures happen behind the line, such as a stale index or a missed review. The blueprint puts an owner on each one.

Trade-offs

What we gain

  • A slow or failed source never slows or breaks a page.
  • The source is asked in one place, so its limits are easy to respect.
  • Live values never reduce the shared page cache hit rate.
  • The source can be swapped later by changing the worker only.

What it costs

  • The value can be a few minutes old.
  • A worker and a cache to run, patch and watch.
  • A blank value needs a design that still makes sense.
  • Agreement with the source's owner on rights and request limits.

When not to use it

  • The value must be exact to the second. Do not show it on the intranet.
  • The value is not live. Use a batch copy (PAT-005).
  • The value is sensitive enough that a stale copy is itself a risk. Do not cache it.

Checks every pattern must pass

Bilingual (official languages law)

The live value is shown as one of a fixed set of values, each translated by us, so English and French ship together. Free text from the source, such as an out-of-office message, is never displayed because it is often written in one language only. Cache age and refresh failures are counted per language.

Accessible (WCAG 2.1 AA)

The value is written as text. Any dot or icon beside it is decorative and hidden from assistive technology (WCAG 1.4.1). A blank value is not announced as an error.

On-premises, no outside connection

The worker, the cache and the source are all on the internal network. Nothing calls out. The worker's service account holds the narrowest rights that work, with credentials from the enclave secret store.

FLAG On-premises conflict

Pattern guidance for live presence usually names Microsoft Teams and Graph, which are cloud services and cannot be reached from the isolated network. The source here must be on-premises.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Does the page render normally when the source is down?
  • Is the source called only by a background worker, in batches?
  • Does a live value stay out of the shared page cache and the search index?
  • Is the value shown as translated text from a fixed set, in both languages?
  • Is the source's request limit written down and respected by the worker?
  • Can the source be swapped without changing the page?
