Pattern catalog / PAT-015

Staff can see, on one page, whether each feature they use is working. The page lists features in everyday words, shows one status for each, and is served separately from the site it reports on, so it still loads when the site does not.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-25
  • Applies: P1, P2, P3, P4, P5
  • Main layer: Website experience

Supports: Staff can tell in seconds whether a feature is working, and the team can tell them early.

  • People and live status
  • Bilingual parity
  • Ownership and freshness
  • Dependencies and delivery

Raised by the EA on 2026-10-25 with a public status page from a Canadian investment firm as the example: one page that lists every feature and its status for end users. The checks, hosting and wording below are the Solution Architect's proposal.

The rule

DO

Publish a status page that lists each staff-facing feature as a component, with one status from a fixed value set, set by automated signals and explained by a short note from a named owner.

DON'T

Rely on a banner inside the main site, or on the help desk, to tell staff something is broken. A banner goes down with the site. Help desk calls pile up and do not tell the next person anything.

When this comes up

  • When search, sign-in or the calendar view stops working, staff do not know if it is them, their browser or the platform.
  • Each person who cannot tell calls or emails the help desk. The same question is asked many times.
  • The team has the facts (logs, heartbeats, checks) but no simple place to share them with staff.

What pulls in different directions:

  • Telling staff early, against not wanting to publish a guess.
  • Plain feature names for staff, against the technical names the team uses.
  • A page that stays up when the site is down, against keeping one more thing to run.
  • Automatic status, against a person who can explain what staff should do.

Picture it

The experience

The page answers one question for staff: is it me, or is it broken? The team gets the same answer from the same signals, and writes one short note.

How it works
  1. List the features in staff words. Pick the things staff do, such as search, find a person, check availability, play a video. Name each one in plain English and French. Do not list servers or software.
  2. Give each feature one owner of record. It is a position, not a person. The owner can explain a problem and say what staff should do.
  3. Use a fixed set of statuses. For example: Working, Slower than usual, Not working, Planned maintenance, Not known. Each has an official English and French name and a plain description.
  4. Let signals set the status. Most come from an automated check that uses the feature like a person would. Others are events the platform already records, such as search index lag or a failed nightly job. A heartbeat shows each source is alive. If a source goes silent, the status becomes Not known. It never stays at Working.
  5. Give each signal a clear power, then add a note. A failed check, or an event past its limit, can change the status. Usage numbers, such as a jump in searches with no results, only flag the owner, because they are slow and noisy. The worst status among the signals wins. The owner then adds a short note in both languages: what is wrong, what staff can do, and when the next update is due. A pre-approved list of notes lets the first notice go out fast.
  6. Serve the page apart from the site. The page is a small static page from its own container, built from the status file. It does not call the CMS, search or the database, so it loads when they do not.
  7. Show history and keep it honest. Show the last 30 days per feature and the dates of past incidents. Never remove an old incident. A fix gets a new entry that says it is resolved.
  8. Tell people, with a link. Staff can opt in to a change notice through the mail relay. The email carries the feature, the status and a link. The detail stays on the page.
Definition cards

Hover or focus any dotted term in this page to see the same definition.

Status page

One page that lists each feature staff use, with a plain status for each one. It is updated by automated checks and explained by a named owner. It is served separately from the features it reports on.

Why it matters hereIt gives staff an answer in seconds and keeps the help desk for problems that are not yet known.

Component

One feature, named the way staff would name it, such as Search or Find a person. A component is not a server or a piece of software.

Why it matters hereStaff cannot act on a server name. They can act on a feature name.

Synthetic check

A small script that uses a feature the way a person would, on a timer, and records whether it worked and how fast.

Why it matters hereIt finds a failure before staff report it, and it measures the same thing every time.

Signal

One piece of evidence about a feature: a check result, a platform event, or an aggregate usage number. Each kind of signal has a rule for what it is allowed to change.

Why it matters hereMore than one signal catches failures a single probe misses, without letting noisy numbers cause false alarms.

Fixed value set

A short, closed list of allowed values for a label that comes from another system. Each value has an English and a French name set by us.

Why it matters hereStops raw text from another system appearing in one language only (principle P2).

Owner of record

The named position accountable for a piece of content: for its accuracy, its review date and the decision to keep, refresh or retire it.

Why it matters hereA position, not a person, so a departure does not orphan the content.

Pointer, not payload

Send or store a link and the minimum needed to recognise the item, not the content itself.

Why it matters hereKeeps content inside the system that owns it and its access rules. Already the rule for notification email.

Trade-offs

What we gain

  • Staff can tell in seconds if the problem is theirs or ours.
  • Fewer duplicate calls to the help desk during an incident.
  • The page still works when the site does not.
  • The same checks feed the operations dashboard, so the data is not collected twice.

What it costs

  • One more small service to build, patch and keep alive.
  • Every listed feature needs a check and an owner. A feature with neither should not be listed.
  • A check can say Working while a real user is stuck. Notes from the owner cover what a check misses.
  • Showing outages and history in the open takes some culture change.
  • Usage numbers are slow and noisy, so they can flag a problem but should not decide the status.

When not to use it

  • The feature is not used by staff directly. Use the operations dashboard, not this page.
  • The audience is people outside the network. That needs its own review and is outside this pattern.
  • There is one feature and one owner. A line on the home page is enough until there are more.
Checks every pattern must pass

Bilingual (Official Languages Act)

Each feature name, each status and each standard note has an official English and French version, so no raw text from a monitoring tool reaches the page. A note cannot be published in one language only. The page counts views per language so the team can see if one language is missed. Status names come from a fixed set that we translate.

Accessible (WCAG 2.1 AA)

Status is written as text beside each feature, never as a coloured dot alone. The page is a plain table with a caption and a 'last checked' time in text. It does not refresh on its own, because that can move focus and cut reading time. A link and a button say where they go. WCAG 2.1 AA is the test; CAN/ASC-EN 301 549 is the target.

On-premises, no outside connection

Everything runs inside the isolated network: the checks, the status file, the static page and the mail relay. Nothing is hosted by an outside status service, and there is no outside script or font. Check scripts and the page build arrive as signed artefacts.

FLAG On-premises conflict

A hosted status service (a public cloud product) is not allowed, even if it is easy. The page must be built and served on the network.


FLAG On-premises conflict

A public status page for people outside the network would need Security and a separate review. This pattern covers staff only.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Can you show the status page loading while the main site is stopped?
  • Does each listed feature have an automated check and a named owner position?
  • If a check stops reporting, does the status change to Not known within a set time?
  • Is every status name and every standard note available in English and French, with no note publishable in one language only?
  • Is status shown as text, and does the page pass an accessibility test with no automatic refresh?
  • Does the page run with no outside service, script or font?
  • Does a change notice carry only a link and a status, not the incident details?
  • Can you show a status change that comes from an event, such as search index lag, and not from a probe?
  • Are usage signals read as aggregate counts per language only, with no one's searches shown?

Open questions for the EA

  • Is the audience staff only, or also the IT support teams? This page assumes staff only.
  • Which features are listed at launch? This page suggests starting with search, find a person and calendar availability.
  • Which position writes the first notice during an incident, and how fast must it go out?
