Pattern catalog / PAT-005

When data is owned by another system, changes slowly, and must keep working when that system is down, we copy it on a schedule into a read-only store and show how old it is.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: Automated, Secure by design, Bilingual parity
  • Main layer: Architecture and platform

Supports: Directory and catalog data always display, even when the source system is down.

  • Integration with other systems
  • People and live status
  • Performance and caching

Found by the Solution Architect in the solution architecture (the people directory (nightly) and the service management catalog (batch) in the Solution Architecture). Not named by the EA. Offered as a candidate pattern, pending EA confirmation.

The rule

DO

Copy the data on a schedule with a queue worker into a read-only CMS store. Keep the source's own identifier. Show when it was last synced.

DON'T

Call the source live while a page is built, or let people edit the copy by hand. The page then fails when the source fails, and the copy drifts away from the source of truth.

When this comes up

  • Some data is structured, owned elsewhere and used on many pages: the people directory, the service catalog.
  • It changes slowly, but the intranet must still show it when the source is down or being patched.
  • Search (PAT-001) finds it. This pattern is for data we show and sort ourselves, such as a directory card or a service list.

What pulls in different directions:

  • Fresh data, against a page that always works.
  • A copy we can render, against one more place the data lives.

Picture it

The experience

A person looks up a colleague or a service and expects it to work, even when the system behind it does not. The page says how current the data is, in words.

Design rules for this pattern

  • Show the data's age in words, next to the data.
  • Keep the card to the agreed minimum fields.
  • Say who fixes mistakes and where.
  • Never let the page wait on the source.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Does the card render, with its date, when the source is switched off?
  • Does a notice appear once data is older than the agreed age?
  • Do English and French cards show the same fields and the same date?
  • Does a hand edit in the CMS disappear at the next run?
  • Is the date readable by a screen reader without colour?
How it works
  1. Agree the contract. The source owner and the owner of record for the copy agree the fields, the schedule and the read-only account. Keep the field set to the minimum.
  2. Read through a documented interface. Use a read-only service account with the narrowest rights that work. Credentials come from the enclave secret store.
  3. Upsert by source ID. Match on the source's identifier, never on a name or title. The copy is read-only in the CMS.
  4. Map labels. Map the source's categories with the taxonomy crosswalk, and its status words to a fixed value set. Anything unmapped goes to a review list.
  5. Handle removals. An item missing from the source gets a tombstone and drops from view after a grace period. Nothing is deleted at once.
  6. Show the age. Every view that shows the data also shows "Data as of" with a date. Past a set age, add a plain notice.
  7. Report the run. Counts of added, changed, removed and failed items, split by language, go to the source owner and the Digital Analytics Lead.
  8. Fix at the source. Errors are fixed in the source system. A hand edit in the CMS is lost at the next run, on purpose.
Definition cards

Hover or focus any dotted term in this page to see the same definition.

Queue worker

A background program that takes jobs from a list and does them one batch at a time, away from any page a person is waiting on.

Why it matters hereIt is the only thing that calls the source, so the source's limits are respected in one place.

Source of truth

The one system that owns a piece of information and is allowed to change it. Every other copy is a convenience that can go stale.

Why it matters hereThe content model only works if each page has one owner and one review date. A second copy has neither.

Owner of record

The named position accountable for a piece of content: for its accuracy, its review date and the decision to keep, refresh or retire it.

Why it matters hereA position, not a person, so a departure does not orphan the content.

Taxonomy crosswalk

A maintained table that says which term in another system matches which term in our shared taxonomy, in both languages.

Why it matters hereOther systems use their own category names. The crosswalk translates them so their content lands under our terms, not beside them.

Fixed value set

A short, closed list of allowed values for a label that comes from another system. Each value has an English and a French name set by us.

Why it matters hereStops raw text from another system appearing in one language only (Bilingual parity).

Tombstone

A marker saying 'this item was removed at the source'. The index uses it to drop the item instead of keeping a result that leads nowhere.

Why it matters hereWithout tombstones, searches keep returning pages that no longer exist.

Data as of

A visible date on a page showing when its copied data last matched the source.

Why it matters hereIt turns a quiet risk (old data) into something a reader can judge.

Journey map

A picture of one person's path through a task, step by step, with what they do, think and feel at each step.

Why it matters hereIt shows where an experience breaks, so we fix the right step and can test it with real staff.

Wireframe

A plain sketch of a screen that shows what goes where. It leaves out final colours, wording and branding on purpose.

Why it matters herePeople can agree on layout, language switch and reading order before anything is built, and a vendor can show the same screen back.

Trade-offs

What we gain

  • Pages stay fast and work when the source is down.
  • The source's limits are respected in one place.
  • One run report shows what failed and why.
  • The source stays the only place to edit.

What it costs

  • Data can be as old as the schedule. Say so on the page.
  • A second copy needs a Privacy Impact Assessment where it holds personal information.
  • Field changes at the source can break the sync. Contract tests are needed.
  • Someone must own the schedule and the alerts.

When not to use it

  • The value changes by the minute, such as availability. Use PAT-006 (read from a cache).
  • We only need people to find the item. Use PAT-001 (index, don't copy).
  • The source cannot be read from the isolated network. Use PAT-003 (reference card).
Checks every pattern must pass

Bilingual (official languages law)

Source labels are mapped to terms we translate. Both language versions of a field come from the source, or are held in our own store with an owner. The run report counts items and failures per language, so a French gap cannot hide in a total.

Accessible (WCAG 2.1 AA)

"Data as of" is text beside the data, not a tooltip or colour alone. Tables from the store use real headers. A stale-data notice is a plain message, not an icon.

On-premises, no outside connection

The job runs inside the network and reads only internal systems. The read-only account and its secret come from the enclave. Nothing leaves.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Can you show a page still rendering, with a "Data as of" date, while the source is switched off?
  • Is the copy read-only in the CMS, and does a hand edit disappear at the next run?
  • Does the sync match on the source identifier and not on a name?
  • Does the run report count added, changed, removed and failed items per language?
  • Does a removed item get a tombstone before it disappears?
  • Does the job use a read-only account with the narrowest rights?

Proposed decision record

Slow-changing data owned elsewhere is synced in batches

Data owned by another system that changes slowly is copied by a scheduled job into a read-only store, keyed by the source ID and shown with a Data as of date. It is not fetched while a page is built.
