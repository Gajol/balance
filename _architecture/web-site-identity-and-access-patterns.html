A web site should not run its own user accounts. It should trust the organization's identity services, and take its roles from the same groups that governance already manages. This note shows the common patterns, one worked example from group to role, and how servers prove who they are to other services.

1. The pieces, in plain words

PieceWhat it does
Active Directory (AD)The directory. Holds people, service accounts and security groups.
ADFSThe on-premises federation service. It reads AD and issues sign-in tokens (SAML or OpenID Connect) to applications.
OpenID Connect (OIDC)Sign-in on top of OAuth. The site gets an ID token that says who the user is.
OAuth 2.0Permission to call an API. It says what a caller may do, not who a person is.
SAML 2.0Older, XML-based sign-in. Still common for packaged and older products.
HashiCorp VaultStores secrets and keys. Can hand out short-lived passwords and certificates to services.
Identity access governance (IAG)The control layer: who asked for access, who approved it, and who reviews it later.

2. Four common patterns

PatternUse it forHow it works, in short
A. OIDC sign-in (authorization code with PKCE)New web sites and single-page appsThe site sends the user to the federation service. The user signs in there. The site gets back an ID token and an access token. The site never sees the password.
B. SAML single sign-onOlder apps, or products that only support SAMLSame idea, but the result is a signed XML assertion posted through the browser. Group membership travels as an attribute.
C. OAuth client credentialsOne service calling another, with no user presentThe calling service proves its identity and gets a short-lived access token for one API.
D. Secrets from VaultDatabase passwords, API keys, certificatesThe service logs in to Vault with its own identity. Vault returns a secret that expires on its own.

Patterns A and B are for people. Patterns C and D are for servers. Most sites use one of A or B, plus both C and D.

Design rule: build the site against the standards (OIDC or SAML), not against ADFS features. If the federation service is replaced later, the site should only need a new trust setting, not new code.

3. From access request to site role

Groups are the thread that connects governance to the site. IAG controls who is in the group. The federation service puts the group into the token. The site turns the group into a role.

Example roles and groups

Site roleAD security groupHow a person gets itWhat they can doExtra controls
End-userWEB-EndUserAutomatic, from a directory attribute such as employee statusRead signed-in content, manage own preferencesSign-in with MFA
Content publisherWEB-PublisherRequested in IAG, approved by the content ownerCreate, edit and publish pagesReview every 6 to 12 months
Platform adminWEB-PlatformAdminRequested in IAG, approved by the platform owner and securityChange configuration, modules, users and deploymentsSeparate admin account, MFA, time-limited, quarterly review, full logging

Anonymous visitors do not sign in. They see public content only and have no group.

Worked example

  1. Request. Alex joins the communications team and needs to publish pages. Alex's manager raises an IAG request for the WEB-Publisher group.
  2. Approve. The content owner approves. IAG checks for conflicts, for example that Alex does not also hold an admin group.
  3. Provision. IAG adds Alex's account to the WEB-Publisher security group in AD.
  4. Sign in. Alex opens the site. The site redirects to the federation service. Alex signs in with MFA.
  5. Token. The federation service reads Alex's groups from AD. A claim rule sends only the groups that start with WEB-. The token is signed.
  6. Map. The site checks the signature, then maps WEB-Publisher to the content publisher role.
  7. Use. Alex sees the editor. Alex does not see admin screens.
  8. Review. At the next review the content owner confirms or removes the access. If Alex leaves the team, IAG removes the group.

What the site receives (simplified ID token claims):

{
  "iss": "https://sts.example.org/adfs",
  "aud": "web-site",
  "sub": "a1b2c3d4",
  "upn": "alex.example@example.org",
  "groups": ["WEB-EndUser", "WEB-Publisher"],
  "exp": 1793300000
}

What the site holds (one mapping, one place):

role_mapping:
  WEB-EndUser:       end_user
  WEB-Publisher:     content_publisher
  WEB-PlatformAdmin: platform_admin
default_role: none        # no matching group means no access

4. Server-to-service credentials

People sign in through the federation service. Servers need their own identity too. Two patterns cover most cases.

Rules that apply to both

  • One identity per service. Never use a person's account, and never share one account across services.
  • Every service account has a named owner. Track it in IAG, review it like a person's access.
  • Prefer keys or certificates to shared secrets for the OAuth client. Limit it to the one API it needs (scope).
  • Short lifetimes. Access tokens in minutes. Vault leases in hours or less. Rotate what cannot expire.
  • Nothing in source control. No secrets in code, build scripts or shared config.
  • Log it. Vault audit logs and token issuance go to central monitoring.

5. Common traps

TrapWhat to do
Too many groups make the token too bigSend only the groups the site needs, filtered by a name prefix such as WEB-.
Removed access still works for a whileKeep token and session lifetimes short. For admin roles, check again before sensitive actions.
Group names spread through the codeMap groups to roles in one configuration. Code checks roles and permissions only.
Admin work done from a daily accountUse a separate admin account with MFA, and give time-limited access where possible.
Locked out if the federation service is downPlan a break-glass account, held in Vault or a sealed envelope, with alerts when it is used.
Tied to one productUse OIDC or SAML standards so the federation service can change without rebuilding the site.

6. Questions to settle with IAM and IAG

  • Is the site a client of OIDC (preferred) or SAML?
  • Who owns each group, and who approves requests for it?
  • Which roles are automatic, and which need approval?
  • How often is each role reviewed?
  • What are the token, session and Vault lease lifetimes?
  • Which service accounts exist, and who owns each?
  • Where do sign-in, role-change and secret-access logs go?

Names, groups and addresses are examples only. Check the current product versions and features in your own environment. Written with help from Claude.ai.
