PAT-001

Index, don't copy

When staff need to find something that lives in another system, we make it searchable. We do not move a copy of it into the CMS.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P2, P3, P4, P5
  • Main layer: Website experience

Supports: Staff find content held in other systems with one search, and always land on the original.

  • Search and findability
  • Integration with other systems
  • Taxonomy and labels

Named by the EA on 2026-10-24 as a pattern to embrace. The detail below is the Solution Architect's proposal.

The rule

DO

Read the other system with a crawler or connector, and put its text, metadata and a link back into the search index. The other system stays the source of truth.

DON'T

Export the other system's content and load it into the CMS as pages, just so search can see it. A copy gets its own owner problem, its own stale date, and its own access rules to get wrong.

When this comes up

  • Staff search once and expect to find everything: pages, the service catalog, archived records, the people directory.
  • Much of it lives in systems we do not own, such as a service management tool and the records system.
  • Copying it into the CMS looks easy. It breaks the ownership and freshness model the project exists to build.

What pulls in different directions:

  • One search box for staff, against one owner per piece of content.
  • Fresh results, against a crawler that must not overload the source system.
  • Their category names, against our shared taxonomy.

Picture it

The experience

Staff search once and expect an answer, whichever system holds it. The pattern keeps that promise without copying anything, so every result is current, owned and opens in the place that decides who may see it.

Design rules for this pattern

  • Show source system, owner and last-changed date on every result.
  • Say so when a result may need sign-in or is not reachable from this network.
  • Keep the same layout, filters and result count in English and French. If one language is behind, say so on the page.
  • Name the destination in link text. Never use "click here".

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Can a tester find the laptop request by typing the same words in English and in French, and reach the original?
  • Does every result show source, owner and last-changed date?
  • Can a keyboard-only user reach, open and leave a result, and does a screen reader read the source label?
  • Does a result from a stopped source disappear after the next crawl, with no dead link left behind?
  • Is click-through shown per language in the analytics tool for the same test?

How it works

  1. Name the source and its owner. The source system and its owner of record agree to be crawled, and agree what is in and out of scope.
  2. Read through the front door. The crawler reads the source as an ordinary staff user would, or calls its documented interface. It never reads the source's database and never needs more rights than a reader.
  3. Normalise. Each item becomes one record with the same fields: title, link, language, type, owner, last changed, and source system.
  4. Map to our terms. The taxonomy crosswalk turns the source's categories into shared taxonomy terms. An item with no match goes to a review list, not into the index untagged.
  5. Index by language. The record goes into the English or French index. A bilingual pair shares one identifier so the two can be matched.
  6. Link back. The result shows the title, a short extract and a link to the original. The source system still decides who can open it.
  7. Remove what is gone. When the source deletes something, the crawler writes a tombstone and the next run drops it from the index.
  8. Measure per language. Crawl lag, record counts and failures are reported separately for English and French.

Source of truth

The one system that owns a piece of information and is allowed to change it. Every other copy is a convenience that can go stale.

Why it matters hereThe content model only works if each page has one owner and one review date. A second copy has neither.

Crawler or connector

A program that visits a source system on a schedule, reads what is there, and hands it to the search index. A crawler follows links; a connector calls the source's own interface.

Why it matters hereHow other systems become searchable without moving their data into the CMS. It runs inside the isolated network and can only reach systems inside it.

Search index

A copy of content organised for fast searching. It holds searchable text and metadata, and a link back to where the content lives.

Why it matters hereThe intranet keeps one index per language in the search engine so neither language can mask the other.

Taxonomy crosswalk

A maintained table that says which term in another system matches which term in our shared taxonomy, in both languages.

Why it matters hereOther systems use their own category names. The crosswalk translates them so their content lands under our terms, not beside them.

Tombstone

A marker saying 'this item was removed at the source'. The index uses it to drop the item instead of keeping a result that leads nowhere.

Why it matters hereWithout tombstones, searches keep returning pages that no longer exist.

Shared taxonomy

One controlled list of terms (topics, divisions, content types) kept in both official languages and applied to content.

Why it matters hereThe same terms drive CMS pages, search facets and analytics reports. It is what lets us ask 'which HR pages are stale, and who owns them?'

Owner of record

The named position accountable for a piece of content: for its accuracy, its review date and the decision to keep, refresh or retire it.

Why it matters hereA position, not a person, so a departure does not orphan the content.

Journey map

A picture of one person's path through a task, step by step, with what they do, think and feel at each step.

Why it matters hereIt shows where an experience breaks, so we fix the right step and can test it with real staff.

Wireframe

A plain sketch of a screen that shows what goes where. It leaves out final colours, wording and branding on purpose.

Why it matters herePeople can agree on layout, language switch and reading order before anything is built, and a vendor can show the same screen back.

Trade-offs

What we gain

  • One owner and one review date per item, still held by the source.
  • Nothing to keep in step: no export job, no second copy to retire.
  • Staff get one search box without us hosting other teams' content.
  • Cheap to add the next source: the same steps, one more crosswalk.

What it costs

  • The index is only as fresh as the crawl schedule.
  • Every source needs a crosswalk, kept up by the Taxonomy / IA Steward.
  • Access is enforced at the source, so we only index content every employee may see.
  • Results can lead to a system with a different look and different accessibility.

When not to use it

  • The content is ours to own. Author it in the CMS instead.
  • Only some staff may see it, and the engine cannot enforce that. Do not index it; link or describe it (PAT-003).
  • The source cannot be reached from the isolated network.

Checks every pattern must pass

Bilingual (official languages law)

Each record goes into the index for its own language. A source item with no partner in the other language is flagged for the owner, never silently indexed alone. Crawl lag and counts are reported per language so a stalled French crawl cannot hide inside a total. Text from the source is shown only as indexed title and extract, never as a status or label we invented.

Accessible (WCAG 2.1 AA)

Results use the same design system search components as every other result. Link text names the destination and the source system, for example 'Request a laptop, in the service catalog'. The language of each result is marked with lang.

On-premises, no outside connection

The crawler, the normalise step and search all run inside the isolated network. It can only reach systems on the internal network. A source that cannot be reached from here is not crawled; use PAT-003, the reference card.

FLAG On-premises conflict

Common crawler and 'federated search' products are sold as cloud services. A proposal that sends source content to a hosted service is non-compliant.

PAT-002

Extract documents in a safe pipeline

A PDF or Office file is untrusted until it has been checked. We scan it, read its text in a sealed container, and only then let search see it.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P1, P2, P3, P5
  • Main layer: Architecture and platform

Supports: Documents become searchable only after they pass a safe, sealed pipeline.

  • Search and findability
  • Security and isolation
  • Ownership and freshness

Named by the EA on 2026-10-24 (PDFs read with a text extraction tool, as a pipeline). The detail below is the Solution Architect's proposal.

The rule

DO

Send every file through the same steps: scan, then read its text with a text extraction tool in an isolated container, then check the language and metadata, then index. A file that fails a step stops and a person is told.

DON'T

Read uploaded or crawled files inside the CMS web process, or index text that has not passed the pipeline. A file parser is software that opens untrusted input, which is exactly where attacks arrive.

When this comes up

  • Search must find words inside PDFs and Office files, not only page text.
  • The files come from many hands: authors, crawled systems, old migrated content.
  • File readers have a long history of security flaws, and nothing on the isolated network refreshes itself.

What pulls in different directions:

  • Searchable text in both languages, against files whose language is unknown.
  • Fast availability after publish, against the time a careful scan takes.
  • Scanned images of text, which need reading by optical character recognition (OCR), against the effort of running it.

Picture it

The experience

A content owner saves a PDF and expects staff to find the words inside it. The checks in between must be quick to explain, hard to get wrong and visible only when a person is needed.

WhoWhat they needWhat goes wrong without the pattern
Content ownerA clear status, and a message only when action is needed.Thinks the upload failed, uploads again, or never learns a file was held.

Design rules for this pattern

  • Show one plain status per file: Checking, Searchable, Held, or Needs attention.
  • Tell the owner only when a person is needed, and say what to do.
  • Show file type, length and language before the person opens a document.
  • Never show a held or unscanned file in search.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Can the owner tell, without help, why a scanned PDF needs attention and what to do?
  • Is an infected test file held, the owner told, and the file absent from search?
  • Does a French test PDF appear only in the French results, and an English one only in English?
  • Is the status readable by a screen reader without colour?
  • Can the operator see one queue with the oldest stuck file first?

How it works

  1. Catch the file. A new or changed file is queued the moment it is saved in the CMS or found by the crawler (tombstone handling is the same as PAT-001).
  2. Scan it. An on-premises malware scan runs first. An infected file is held in quarantine and its owner is told. Nothing reaches the next step.
  3. Extract in a sealed container. a text extraction tool runs in its own container with no network access, a memory limit and a time limit. A file that hangs or crashes it is stopped, not retried forever.
  4. Return only text and metadata. The container hands back plain text and the file's properties. The file itself is not passed on.
  5. Check the language. Use the language the author set in the CMS. For a crawled file with no language, use detection only above a confidence threshold. Below it, the file goes to the review queue.
  6. Read the signals. A PDF with no text layer is a scan: queue it for OCR if the department supports it, or flag it. An untagged PDF is reported to the content health report as an accessibility gap.
  7. Index. The text, the title, the owner, the last-modified date and the shared taxonomy terms go into the English or French index.
  8. Keep the evidence. Every file records its scan result, extraction result and time, so the pipeline can be audited.

Trade-offs

What we gain

  • Words inside PDFs and Office files become findable.
  • A broken or hostile file cannot reach the web server or the database.
  • One path for every file, so one place to log, patch and audit.
  • Gaps in accessibility and language show up as a by-product.

What it costs

  • Another set of components to patch on a network where nothing refreshes itself: scanner signatures, a text extraction tool, OCR packs.
  • A delay between save and searchable, because scanning and extraction take time.
  • A review queue someone must own, or failed files pile up.
  • OCR quality is uneven, especially for French diacritics and poor scans.

When not to use it

  • The file will never be searched or crawled (for example a download-only form). Store it, but do not index it.
  • The file must be kept as a record. The pipeline does not archive; archiving follows.
  • A file is too large or odd to extract. Index its title and metadata only, and say so in the record.

Checks every pattern must pass

Bilingual (official languages law)

The file's language is set by the author in the CMS, not guessed. Detection is a fallback with a confidence threshold, and uncertain files are queued for a person. Extraction success, failures and queue age are reported per language. Where OCR is used, both English and French language packs are installed and tested, because an English-only pack silently garbles French accents.

Accessible (WCAG 2.1 AA)

Extraction exposes untagged and image-only PDFs. Those are reported in the content health report so owners fix them (WCAG 2.1 AA, CAN/ASC-EN 301 549). The pipeline does not make a document accessible; it makes the gap visible.

On-premises, no outside connection

Scanner, a text extraction tool, OCR and search all run in containers on the internal network. Signature and model updates arrive as signed artefacts through the same low-side to high-side pipeline as code. No online file converter or hosted OCR service is allowed.

FLAG On-premises conflict

Hosted document-AI and 'cloud OCR' services are commonly suggested for this job. Each sends the file outside the network. Non-compliant.

PAT-003

Reference card

When staff need something we cannot link to or copy, we publish a short page about it. The page has a title, an owner and a review date, so it is found, measured and kept fresh like everything else.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P2, P3, P4
  • Main layer: Website experience

Supports: Staff find an owned, reviewed page for a system they cannot reach, instead of a dead link.

PAT-004

Pointer, not payload

A message says that something happened, which item it is about, and where to go. It never carries the content itself.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P1, P2, P5
  • Main layer: Content and governance

Supports: Reminders and digests reach people without carrying content out of the intranet.

  • Messages and reminders
  • Security and isolation

Found by the Solution Architect in the solution architecture (where it governs notification email). Not named by the EA. Offered as a candidate pattern, pending EA confirmation.

The rule

DO

Send a pointer, not payload message: the event, the item's title, a link and a date. Let the person open the link, signed in, to see the content.

DON'T

Paste the content into the message so people need not click. The copy then outlives every permission change and sits in mailboxes, phones and archives we do not control.

When this comes up

  • The intranet must reach people: a review is due, a page was flagged, something is waiting. Email is the only reachable channel in the first release (related decision, related decision).
  • Email is the one place where information leaves the intranet's access model. Inside the site, CMS decides who sees a page. In an inbox, forwarding rules, phone sync and local archives decide.
  • Stakeholders will ask why the email does not just say what changed. It sounds helpful and it is the easy path.

What pulls in different directions:

  • Short, useful messages, against the temptation to include everything.
  • Staff convenience, against records and access-to-information exposure.

How it works

  1. Name the event. List the few events that may send mail: review due, flagged, correction required, queued, archived. Anything else needs a record.
  2. Write the template as a pointer. Allowed: event, page title, link, due date, affected language, who acted (role and name), a count. Not allowed: body text, comments, attachments, personal information about a third party.
  3. Keep the subject line to the event. No content in the subject. It shows in preview panes on shared screens.
  4. Suppress sensitive titles. Content types and sections marked title suppression send "A page you own needs review" and a link, nothing more.
  5. Send both languages in one message. English block, then French block. Never guess the recipient's language.
  6. Prefer a digest. Daily for the review queue, weekly for coming review dates. Send at once only for a required correction or an unpublish.
  7. Act in the intranet only. No approve, publish, retire or clear-a-flag by email reply. The action happens signed in, where it is logged.
  8. Enforce it in code review. The no-content rule is tested on the template. A guide alone will not hold it.

  • Status: Proposed, pending EA confirmation

The rule

DO

Copy the data on a schedule with a queue worker into a read-only CMS store. Keep the source's own identifier. Show when it was last synced.

DON'T

Call the source live while a page is built, or let people edit the copy by hand. The page then fails when the source fails, and the copy drifts away from the source of truth.

  • Some data is structured, owned elsewhere and used on many pages: the people directory, the service catalog.
  • It changes slowly, but the intranet must still show it when the source is down or being patched.
  • Search (PAT-001) finds it. This pattern is for data we show and sort ourselves, such as a directory card or a service list.

  • Fresh data, against a page that always works.
  • A copy we can render, against one more place the data lives.

How it works

  1. Agree the contract. The source owner and the owner of record for the copy agree the fields, the schedule and the read-only account. Keep the field set to the minimum.
  2. Read through a documented interface. Use a read-only service account with the narrowest rights that work. Credentials come from the enclave secret store.
  3. Upsert by source ID. Match on the source's identifier, never on a name or title. The copy is read-only in the CMS.
  4. Map labels. Map the source's categories with the taxonomy crosswalk, and its status words to a fixed value set. Anything unmapped goes to a review list.
  5. Handle removals. An item missing from the source gets a tombstone and drops from view after a grace period. Nothing is deleted at once.
  6. Show the age. Every view that shows the data also shows "Data as of" with a date. Past a set age, add a plain notice.
  7. Report the run. Counts of added, changed, removed and failed items, split by language, go to the source owner and the Digital Analytics Lead.
  8. Fix at the source. Errors are fixed in the source system. A hand edit in the CMS is lost at the next run, on purpose.

How it works

  2. Ask in batches, off the page. A queue worker asks the source for many items at once, on a schedule, within the source's limits.
  3. Write value and age. The live-value cache stores the value with a short life. It can be served a little stale while a refresh is queued.
  4. Read through a placeholder. The page leaves a lazy placeholder where the value goes. It reads the cache only.
  5. Fail quiet. If the cache is empty or the source is down, the value is blank and the page renders as normal.
  6. Keep it out of the shared cache and analytics. The value never enters the page cache, search or analytics.
  7. Show it as words. Use a fixed set of values, translated by us (see PAT-007), never colour alone.
  8. Measure. Report cache hit rate, value age and refresh failures per language.

DO

PAT-012

Cross the boundary as signed artefacts

Anything that crosses into the isolated network crosses as a signed, scanned package from a known build. It never arrives as a download or a hand copy.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P5, P3
  • Main layer: Architecture and platform

Supports: Everything entering the isolated network is built, signed and verified first.

  • Dependencies and delivery
  • Security and isolation

Found by the Solution Architect in the solution architecture (which sets a signed-artefact pipeline into the isolated network). Not named by the EA. Offered as a candidate pattern, pending EA confirmation.

The rule

DO

Build and sign the signed artefact on the low side, carry it across by the Security-owned transfer, and check the signature on the high side before anything runs.

DON'T

Copy files, pull packages or download updates straight into the isolated network. Nothing there can tell a good file from a bad one, and nothing there refreshes itself.

When this comes up

  • The isolated side has no internet and no automatic updates. Everything it runs must be brought in.
  • Many things must cross: code, container images, scanner signatures, models, taxonomy files, mirrored packages.
  • A quick hand copy is tempting during an outage. It bypasses the only check the network has.

What pulls in different directions:

  • Speed in a hurry, against a trusted chain.
  • Fewer steps, against proof of where a file came from.

Picture it

  • Show each step's result in words.
  • A failed check stops the release and says why.
  • Say when a change will reach staff.
  • Ship both languages together.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Can a release manager see every step, its result and its owner on one page?
  • Does a bad signature stop the release on the high side?
  • Does the same artefact run in staging and production?
  • Do English and French strings ship in the same release?
  • Is the staff notice clear, dated and in both languages?

How it works

  1. List what crosses. Code, container images, scanner signatures, models, taxonomy files and mirrored packages are all artefacts. If it is not on the list, it does not cross.
  2. Build once on the low side. The pipeline builds from version control. The image is the unit of deployment (related decision).
  3. Scan and write the SBOM. Run the checks and record every component in an SBOM.
  4. Sign it. The build signs the artefact. The signing key is held by the pipeline, not by a person.
  5. Hand to Security. A Security-owned procedure carries the artefact across (related decision). The transfer is one way and logged.
  6. Verify first. The high-side pipeline checks the signature and the SBOM before any install. A failed check stops the line.
  7. Prove on staging. The same artefact goes to staging with real data and real integrations, then to production (related decision).
  8. Keep the record. For each artefact: who built it, who approved the transfer, when it was verified and where it runs.

PAT-013

Check accessibility at every gate

Accessibility is tested automatically at three points: when we build, when someone publishes, and on the live site every week. People test the rest. Nothing relies on one audit at the end.

  • Status: Proposed, pending EA confirmation
  • Version 0.1 · 2026-10-24
  • Applies: P1, P2, P3
  • Main layer: Content and governance

Supports: Accessibility is checked at the build, at publishing and on the live site, with proof for audit.

  • Accessibility assurance
  • Accessible experience and plain language
  • Bilingual parity
  • Measurement and analytics

Requested by the EA (add accessibility under Content and governance, with checks in the build pipeline and at publishing). Drafted by the Solution Architect from principle P1 and. Pending EA confirmation.

The rule

DO

Run an accessibility gate at the build, at publishing and on the live site, in English and French. Keep the results as evidence and give every finding an owner.

DON'T

Rely on one audit before go-live, or on a tool alone. Never remove live content because a tool complained. A person decides.

When this comes up

  • WCAG 2.1 AA is a pass or fail rule (P1). A page that fails is a barrier for some employees and a finding at audit.
  • Problems arrive from two sources: code (templates, theme, components) and content (images, headings, links, documents, video). A check on only one of them misses half.
  • Content changes every day. A site that passed at go-live can fail next month, and French pages can fail in ways English pages do not.
  • Automatic tools find only part of the problems. The rest needs people, including people who use assistive technology.

What pulls in different directions:

  • Strict gates, against authors who need to publish.
  • Automatic speed, against human judgment.
  • One shared standard, against two languages with different text lengths.

Picture it

The experience

An author is told about a problem while writing, in plain words, and fixes it before publishing. The designer and the content manager see one view of what is failing, in each language.

Content authorClear advice while writing and a plain reason when a draft is held.A vague block at the last minute.

ExecutivesA simple, honest view of accessibility and the gaps.A green score that hides a French failure.

Design rules for this pattern

  • Say what is wrong, where, and how to fix it, in plain words.
  • Separate errors that hold from advice that guides.
  • Never use colour alone to show a problem.
  • Show the same help in English and French.

How to test the experience

Check these with real staff, in English and in French, and with a screen reader. The pattern is met if the answer to each is yes.

  • Does a missing alt text hold a draft with a plain message?
  • Does a failed build test stop a release from being signed?
  • Do English and French pages show their own results?
  • Can a keyboard user reach every advice note?
  • Can a finding be traced to an owner and a due date?

How it works

  1. Set the standard. WCAG 2.1 AA is the pass or fail line. CAN/ASC-EN 301 549 is the stated target. Both are tested in English and French.
  2. Use first-class parts. Build on design system components without overriding their markup, and on first-class modules. Fewer custom parts means fewer new failures.
  3. Gate 1, the build. Every change to code runs axe-core through a test runner on a fixed set of pages, in both languages and at phone and desktop widths. A failure stops the build. No artefact is signed (related decision, PAT-012).
  4. Make the build set realistic. The test pages cover every content type and component, with long French text and 200% zoom, so layout failures show before release.
  5. Gate 2, authoring. The editor shows problems as the author writes. Machine-certain errors hold the draft: missing alt text, empty links or headings, skipped heading levels, video with no caption file. Judgment items, such as link wording, only advise.
  6. Hold, never remove. A gate may stop a draft from going live. It never takes live content down. A finding on live content is a flag (PAT-009) to the owner of record.
  7. Gate 3, the live site. A scheduled crawl runs inside the network against live English and French pages and files. It reports per language (PAT-011) into the content health report.
  8. Test with people. Before go-live and each release, staff test with NVDA, JAWS and keyboard only. Employees who use assistive technology test real tasks. Every page has an accessibility feedback link that joins the same log.
  9. Keep the evidence. One log holds each gap, its owner, a fix date and the release that closed it. It is reviewed each release. This is the audit evidence and the base of the conformance report.
  10. Waivers are short. A known issue may be waived only with a named owner, a reason and an end date. An expired waiver fails the gate again.

Conformance report

A written statement of how a product meets each clause of a standard, with the gaps and the plan to close them.

Why it matters hereIt is the evidence an auditor asks for. EN 301 549 and the federal accessibility law both lean on it.

First-class modules

Modules that ship inside CMS core and are built, tested, secured and released by the CMS core team, on the same schedule as core. Examples: Language, Content Translation, Workflows, Content Moderation and Media. Contributed and custom modules are not first-class.

Why it matters hereA first-class module is patched when core is patched and needs no extra vetting. Everything else is a permanent patch duty for us, so it must pass the admission path first (PAT-010). The RFP asks vendors to use first-class modules wherever they can.

Content health report

A scheduled report that joins CMS metadata (owner, review date, language) with analytics traffic to show what is stale, unowned or unread.

Why it matters hereIt is the evidence that content is owned and being refreshed or disposed of, per language.

Signed artefact

A built package, such as a container image, with a digital signature that proves who built it and that it has not been changed.

Why it matters hereOn the isolated network nothing can fetch or check a file for itself. The signature is how we know a file is the one we built.

Service blueprint

A picture of a service in layers: what the person sees, and what staff and systems do out of sight to make it happen. A line of visibility separates the two.

Why it matters hereMost intranet failures happen behind the line, such as a stale index or a missed review. The blueprint puts an owner on each one.

Wireframe

A plain sketch of a screen that shows what goes where. It leaves out final colours, wording and branding on purpose.

Why it matters herePeople can agree on layout, language switch and reading order before anything is built, and a vendor can show the same screen back.

Trade-offs

What we gain

  • Problems are found when they are cheap to fix.
  • Releases cannot make accessibility worse without someone choosing it.
  • Evidence for audit builds up as work goes on.
  • French and English are proven equal, with numbers.
  • Authors learn from advice while they write.

What it costs

  • Automatic tools find only part of the problems. People are still needed.
  • Gates can slow an urgent release or a publish.
  • False alarms need tuning, and a noisy gate gets ignored.
  • Each tool outside core is a patch duty.
  • Someone must triage the findings each week.

When not to use it

  • A throwaway draft that never leaves the author's workspace.
  • A third-party tool the department cannot change. Record the gap in the log and plan the fix instead.

Checks every pattern must pass

Bilingual (official languages law)

Every gate runs on English and French pages and reports each language separately. French is tested for its own failures: language tags, longer text, reflow at 200% zoom. Neither language is the default.

Accessible (WCAG 2.1 AA)

This pattern is the proof. Its own screens meet WCAG 2.1 AA. Findings are written in words with the rule name, not only a colour or a score.

On-premises, no outside connection

Every tool runs inside the network from internal mirrors. Nothing calls an outside scanner or a hosted checker. Tools arrive as signed artefacts (PAT-012).

FLAG On-premises conflict

Hosted checkers (for example browser extensions that send pages to a vendor, or online scanners) are not allowed. Use self-hosted tools only.


FLAG On-premises conflict

A tool that loads scripts from a CDN at run time fails the constraint. Bundle everything inside the artefact.

How to test a vendor proposal

Ask the vendor to show, not tell. The pattern is met if the answer to each is yes.

  • Show a build that fails because an accessibility test failed, and show that no artefact was signed.
  • Do the build tests run on English and French pages, at phone and desktop width?
  • Show a draft held for missing alt text, and a video held for a missing caption file.
  • Does a gate ever remove live content on its own?
  • Show a scheduled crawl of live pages with results per language, with no outside connection.
  • Which parts of the checks need a person, and who does them?
  • Can you produce the findings log and conformance report for any release?
  • List every accessibility tool you propose, where it comes from, and its licence.
