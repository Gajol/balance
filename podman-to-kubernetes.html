Podman to Kubernetes: Moving a Web Platform Without Rework

Working paper. Build the deployment as Kubernetes YAML from day one, run it on Podman now, and move to a cluster later without a rewrite.

Contents

    Executive summaries

    Four short versions, one per audience. Each stands alone.

    A. Delivery team executive summary: "How do we build this?"

    One sentence: A standard open-source CMS, search engine and analytics tool, packaged as signed container images, built once outside the isolated network, carried across under Security's procedure, and deployed unchanged. We start on Podman. The same definitions later run on Kubernetes.

    Talking points

    1. Three services, all open source, all mainstream. The CMS core, a search engine for search, an analytics tool for analytics. No custom platform. Core and first-class modules first.
    2. Build once, deploy many. Images are built on the build side from internal mirrors, tested, signed and listed in a manifest with checksums. Nothing is built, downloaded or fixed by hand inside the isolated network.
    3. Same image in every environment. Alpha, then development, staging and production. Only configuration and scale change. What we test is what we approve is what we run.
    4. Portable by design. Deployment is written as Kubernetes YAML even while it runs on Podman. Moving to Kubernetes later adds things (ingress, storage classes, policies). It does not rewrite things.
    5. State is kept outside the app. Database, CMS files, Search index and Analytics data sit on managed storage. That is what makes rollback and moving platforms safe.
    6. Bilingual is measured, not claimed. EN and FR are tracked separately for search indexing lag, traffic and accessibility. A stalled French queue cannot hide inside an average.
    7. Content freshness and ownership come from the stack. CMS metadata joined with Analytics traffic, reported to owners and executives.

    What we ask teams to show (we evaluate; we do not dictate the design): - How their design keeps the move to Kubernetes small. - How every dependency reaches the isolated network with no public source at install or run time. - How they prove EN/FR parity on an ongoing basis. - How they restore Search and CMS files from backup, on both platforms.

    Likely questions

    Question Short answer
    Why Podman first? Lower platform prerequisite and a faster start. Kubernetes follows when the organization platform is ready.
    Why not just wait for Kubernetes? The project should not be gated on a platform it does not control. Portable design removes the gate.
    Can we use cloud services? No. On-prem, isolated. A cloud dependency fails the constraint.
    Can we use Helm charts and operators? Only if vendored, mirrored and justified as a patch cost. Plain YAML is preferred where it is not much harder.
    Who patches? Build side rebuilds from refreshed mirrors. Updates cross the gap by the same signed path.
    Hardest part? Search on Kubernetes, then backup and restore.

    B. IT executive summary

    • What IT is asked to provide: a Podman host pattern now; later, an approved on-prem Kubernetes platform with fast block storage (Search), shared read-write-many storage (CMS files), an ingress controller, an internal certificate process, secret delivery and log/metric collection.
    • What stays the same at the move: the images, the configuration, the pipeline promotion rule, the EN/FR checks.
    • What changes: storage, networking, secrets, scheduling, backups, rollout method, and patching of the cluster itself.
    • Effort hot spots: Search (clustered state), backup and restore, and cluster security approval.
    • Capacity (section 15): on Podman, about 11% more vCPU and 9% more RAM than the sizing baseline. On Kubernetes, 104 vCPU and 242 GB for the containerized part if staging mirrors production, against 68 and 164 on Podman.
    • Databases stay where they are¹: on non-containerized servers run by the database team. Agree the firewall allow-list and connection limits for the new platform early.
    • Operating model: Communications consumes the site as a service. IT owns the platform and the Analytics platform instrumentation.
    • Decisions IT can make early: does the platform exist, storage on offer, operator and chart policy, and how long Podman is expected to serve as production.
    • Ongoing cost: every added component is a permanent patch obligation on a network that does not refresh itself. Mirror cadence needs a named owner.

    C. Security executive summary

    • Posture: isolated. Production is deploy-only. No outbound connection is required or permitted at any stage.
    • Provenance: commit, build, signature, manifest, transfer, deploy. The assessor can trace every running container back to a source commit.
    • Transfer: Security owns the crossing procedure. It carries images, but also deployment definitions, Ansible content, platform images and the Search configset, all signed and checksummed.
    • Phone-home controls: CMS update checks, Analytics internet features, marketplace installs and GeoIP downloads are switched off and verified. See section 2.
    • Container hardening: non-root, read-only root filesystem, dropped capabilities, resource limits, no host paths.
    • Network: default deny. On Kubernetes, NetworkPolicy allows only the paths needed (for example, only CMS reaches Search). On Podman, the host firewall does the same job.
    • Secrets: from the isolated network secret store. Not in images, not in Git.
    • Database path¹: TLS to the database servers, egress limited to the database host and port. After the move the database sees new source addresses, so firewall rules need a planned change.
    • Security approval: Podman stage is approved first. Moving to Kubernetes needs a security re-assessment of the cluster deployment. Evidence from the Podman stage can be reused where the image is unchanged.
    • Security asks: an admission rule that only signed images run, internal-only certificate authority, and a verified egress test on each environment.

    D. Project manager summary (non-technical)

    What will happen, in plain terms

    1. Build the pieces once, outside the secure network. The delivery team builds the website, search and analytics as sealed packages.
    2. Show people early. A short-lived trial environment lets stakeholders see and use the core ideas.
    3. Carry the packages across the secure gap. Security checks and approves each crossing.
    4. Install on the secure network. First development, then staging (a dress rehearsal with real content), then production.
    5. Accredit, then go live.
    6. Later, move to a bigger platform (Kubernetes). This is planned for from the start so it is a move, not a rebuild.

    Why the architecture guidance makes this efficient

    • Same package everywhere. Fewer surprises between test and production.
    • Rules set up front. The delivery team builds it portable now, so the later move is mostly adding things.
    • Standard parts. CMS, Search and Analytics are widely known. Fewer special skills needed.
    • Early proof. Rehearsing the crossing and the restore finds problems early, when they are cheap.

    What the PM should watch

    Watch item Why it matters
    Does the organization have an approved Kubernetes platform? Longest lead time. Gates the later move, not the first release
    Storage for the move (shared files, fast disks) Cannot be added at the last minute
    Cleared staff with access to the secure network Narrows who can do the work
    Someone owns refreshing the internal software mirrors Otherwise the secure side falls behind on security fixes
    Capacity for the Kubernetes stage (section 15) More vCPU and RAM than Podman: node overhead, a three-pod ZooKeeper, spare capacity, and a production-like staging
    Database firewall rules for the new platform¹ Database sees new source addresses after the move
    Re-security approval after the move Plan the time early
    Staging environment ready before install Needed for real-data checks

    1. Bottom line

    • Starting on Podman and moving to Kubernetes later is a sound plan, if the work is built portable from day one.
    • The images do not change. The wrapper around them does: networking, storage, secrets, scheduling, scaling.
    • The cheapest way to keep the move small is to write the Podman deployment as Kubernetes YAML and run it with podman kube play. Then the later move is mostly adding things, not rewriting.
    • Search is the hardest to move. CMS is medium. Analytics is easiest.
    • The biggest risk is not technical. It is the Kubernetes platform itself: it must exist on-prem, be approved, and be able to run this workload.

    2. Isolated-network constraint: how this paper stays inside it

    Short answer: this paper stays inside the isolated network constraint. Nothing in it requires an outbound connection at any stage. The list below names the places where a default setting could quietly break that, and what to do about each. Items marked verify depend on the exact version we pin and must be tested, not assumed.

    2.1 Where things happen

    Activity Where Rule
    Build, test, scan and sign images Build side, from internal mirrors Nothing fetched from the public internet
    Resolve packages (Composer, npm, OS, Ansible collections) Build side only The isolated side cannot resolve anything
    Carry across Security-owned transfer procedure Signed artefacts, manifest, checksums
    What is carried Images, deployment YAML and overlays, Ansible roles and collections, Search configset, Kubernetes platform images, GeoIP data, plugin packages Not just application images
    Run on Podman Alpha on the build side, then dev, staging and production on the isolated side Deploy-only in production
    Run on Kubernetes Isolated side Same artefacts, same path
    Fix or change in production Never interactively Rebuild on the build side, transfer, redeploy

    2.2 Flags

    • Flag: No public registries. Images, Helm charts, operators and Kubernetes add-ons must all come from the internal registry. Anything that pulls from a public source at install or run time fails the constraint.
    • Flag: No cloud storage classes. Persistent volumes come from on-prem storage. Shared (read-write-many) storage is needed for the CMS files directory.
    • Flag: Operators and Helm charts are new dependencies. Each is a permanent patch obligation on a network where nothing refreshes itself. Keep a local copy of the charts. Mirror the images. Prefer plain YAML where it is not much harder.
    • Flag: Applications must not phone home. Switch these off and test that they stay off:
    • Analytics: marketplace, update checks and other internet features (the enable_internet_features setting; verify on the pinned version), plus GeoIP auto-download.
    • CMS: the Update Status module, which contacts the project's update server. Do not install it, or disable its checks. Updates arrive only through the pipeline.
    • Search: no external plugin or package repository.
    • Flag: Kubernetes bootstrap images. The platform itself needs images (pause image, networking plugin, DNS, ingress controller, metrics). All must be mirrored. A node that tries to pull from a public registry will fail or, worse, succeed on the wrong network.
    • Flag: Podman infra image. podman kube play creates a small helper ("infra") container per pod. Verify it is built or mirrored locally and never pulled externally.
    • Flag: Certificates. Automatic public certificate issuance (ACME, such as Let's Encrypt) is not allowed. Use the organization's internal certificate authority. Certificate revocation checks must also point to internal responders.
    • Flag: Tooling that fetches by default.
    • Kustomize: no remote bases. Every base and overlay is in the repository.
    • Ansible: only ansible.builtin modules or vendored collections. No Galaxy at run time.
    • the CI tool: no include: from outside, and no image: from a public registry.
    • kubectl and podman: installed from internal mirrors.
    • Flag: Time and name services. Internal NTP and internal DNS only.
    • Flag: The Kubernetes platform needs its own security approval. If the organization does not have one, this is a project dependency with its own lead time.

    2.3 Isolated-network acceptance checks

    Run on every environment, and again after the move to Kubernetes.

    # Check Evidence
    1 Egress test: from each pod or container, outbound connections fail Test log
    2 Every running image digest appears in the signed manifest Digest comparison
    3 No image reference points outside the internal registry Scan of rendered YAML
    4 Analytics and CMS update and marketplace checks are off Config export and run-time test
    5 Platform bootstrap images all come from the internal registry Node image list
    6 Certificates issued by the internal CA only Certificate chain
    7 A rebuild from the transferred artefacts alone succeeds Rehearsal record

    3. Design rules to follow now (so the move is small)

    # Rule Why it matters later
    1 Build standard OCI images only. No Podman-specific tricks inside the image The same image runs on both
    2 One process per container. app server, web server, Search, Analytics each separate Maps directly to pods and containers
    3 Keep web-server and app server in one pod (shared localhost) Works the same in a Kubernetes pod
    4 All config from environment variables or mounted files. Nothing baked in per environment Becomes ConfigMaps and Secrets
    5 No host paths. Use named volumes / claims only Host paths do not exist in Kubernetes
    6 Give every container a health endpoint and define probes now podman kube play honours probes; Kubernetes needs them
    7 Set CPU and memory limits now Kubernetes scheduling depends on them. Search heap depends on them
    8 Run non-root, read-only root filesystem, writable temp dirs only Matches Kubernetes pod security rules
    9 Scheduled jobs are separate from web containers Become CronJobs
    10 Deploy steps are scripted (database updates, config import, cache rebuild) Become a Job or Helm hook
    11 State lives outside the app container: database¹, files, Search index, Analytics data Moves without touching the app
    12 Keep EN and FR per-language metrics in the monitoring design Provable bilingualism must survive the move

    4. Podman options compared

    Option Looks like Migration effort Verdict
    podman kube play on Kubernetes YAML, run under systemd with Quadlet .kube units Kubernetes YAML Low Recommended
    Quadlet .container files systemd units per container Medium. Rewrite as YAML later Good fallback
    podman-compose / Compose files Compose YAML Medium to high. Tool-assisted conversion needs cleanup Not recommended
    Raw podman run scripts Shell High Rejected. Not repeatable, no provenance

    Gaps in podman kube play to plan for:

    • It does not give you Ingress, NetworkPolicy, or real Services. Use the reverse proxy cache container as the front door on Podman.
    • Scheduled jobs: use systemd timers on Podman. They become CronJobs on Kubernetes. Check whether the pinned Podman version handles Job and CronJob objects before relying on them.
    • No rolling updates, no automatic rescheduling. Podman gives restart on failure, not high availability.

    5. What changes, by area

    Effort: L low, M medium, H high.

    Area On Podman On Kubernetes Effort
    Image supply Internal registry, signed images Same registry. Add admission control that only allows signed images L
    Networking Podman network, reverse proxy cache as front door Ingress controller, Services, DNS, TLS secrets M
    Network rules Host firewall NetworkPolicy (default deny, then allow) M
    Storage Named volumes on host or NFS StorageClass, PersistentVolumeClaims, RWX for CMS files H
    Config Env files, mounted files ConfigMaps L
    Secrets Podman secrets / isolated network store Kubernetes Secrets backed by the isolated network secret store M
    Scheduling systemd timers CronJobs L
    Deploy steps Script run by the pipeline Job or Helm hook, ordered before rollout M
    Scale and HA One instance, restart on failure Replicas, rolling updates, pod disruption budgets M
    Security Rootless Podman Pod Security Standards, RBAC, service accounts M
    Logging journald Cluster log collection to the on-prem log platform M
    Metrics Host exporters Cluster metrics, per-pod scrape M
    Backups Volume copy, database dump Volume snapshots plus app-level backups H
    Database access¹ Fixed host IP to the DB server Traffic leaves from node or egress IPs. Egress NetworkPolicy to DB host and port M
    Patching Rebuild image, restart unit Rebuild image, rolling update. Plus patching the cluster M

    6. Component by component

    6.1 CMS (app server + web server)

    Impact: medium. The application is stateless except for files and sessions.

    Topic Podman Kubernetes Action now
    Files directory Local or NFS volume RWX volume shared by all pods Pick shared storage design now. Never rely on local disk
    Config settings.php reads env vars Same, from ConfigMap and Secret Make settings.php fully env-driven
    Cron systemd timer runs cms-cli cron CronJob Keep cron out of the web container
    Queue workers Separate container or timer Separate Deployment Split Search indexing and archive-API workers from web
    Deploy steps Script: updb, cim, cr One-shot Job before rollout Script them now, idempotent
    Sessions and cache Single instance, so easy Many pods need a shared cache (Redis) Use Redis from the start
    Reverse proxy Reverse proxy cache sets headers Ingress sets headers Set trusted proxies and host patterns by env var
    Temp and private files Writable volume emptyDir for temp. Claim for private files Declare both paths explicitly
    Update checks Update Status module would call the project's update server Same Do not install it, or disable it. Updates arrive only through the pipeline

    Work to move: Deployment with 2+ replicas, Service, Ingress, CronJob, deploy Job, RWX claim, Redis, probes, NetworkPolicy.

    Watch for: read-only root filesystem breaking CMS writes. Cache behaviour between replicas. Authenticated pages caching differently from anonymous ones.

    6.2 Search

    Impact: high. Search holds state, needs tuned memory, and is clustered differently on Kubernetes.

    Topic Podman Kubernetes Action now
    Mode Single node StatefulSet, ideally cluster mode with a 3-node ZooKeeper Run cluster mode with one Search and one ZooKeeper container on Podman, so configsets and collections are managed the same way
    Config Config files in image or volume Configset in ZooKeeper, uploaded by a Job Package the configset as an artefact. Upload with a script, not by hand
    Storage Named volume One PVC per Search pod (fast local-class storage) Size for the index. Keep it off shared NFS if possible
    Memory Container limit and heap set together Same, but pod limit must exceed heap by a margin Set heap to about half the memory limit now. Leave room for OS cache
    File limits --ulimit nofile on run Inherited from the runtime. Not set per pod Confirm the node and runtime allow high open-file limits
    Permissions :U volume flag, runs as uid 8983 fsGroup: 8983 or an init container Do not run as root to fix permissions
    Backups Collection backup API to a mounted path Same API to a backup claim Test restore, not just backup
    Reindexing Rebuild from CMS Same Keep it a one-command job. It is also the recovery plan
    Bilingual Per-language fields and analysers Same EN and FR index lag tracked separately

    Work to move: StatefulSet, headless Service, ZooKeeper ensemble (or operator), configset Job, backup CronJob, PVCs, anti-affinity so replicas land on different nodes, NetworkPolicy so only CMS reaches Search.

    Watch for: switching from single node to cloud mode late. It changes how collections, replicas and configsets work, which is why the Podman setup above runs cloud mode from day one. Operator or chart choice is a patch obligation. Decide deliberately.

    6.3 Analytics

    Impact: low to medium. Mostly a PHP app with a database and one heavy scheduled job.

    Topic Podman Kubernetes Action now
    Config file config.ini.php is written by the installer Cannot simply be a read-only ConfigMap Generate it at build or first-run. Use environment-variable overrides where the pinned version supports them
    Archiving systemd timer runs core:archive CronJob, concurrency forbidden Turn off browser-triggered archiving now
    Plugins Baked into image Same No marketplace installs in an isolated network. Pin plugin versions in the image
    GeoIP Database file mounted Same, from a claim or the image Supply the database offline. Never auto-download
    Internet features Off in config Off in config Disable update checks and marketplace. Verify on the pinned version, and test
    Tracking load One instance Scale web pods. Optional queued tracking with Redis Not needed on day one. Do not rule it out
    Writable paths tmp/ volume emptyDir for tmp/. Claim for anything that must persist List every writable path
    Database External External Unchanged
    Reporting pipeline Reads Analytics API Same, through an internal Service Keep API access internal only
    Audiences Role-based access Same Unchanged. IT owns platform. Comms owns reports

    Work to move: Deployment, Service, Ingress path for the tracking endpoint, CronJob for archiving, config generation, NetworkPolicy, probes.

    Watch for: the content-freshness reporting job. It depends on archiving finishing on time, so alert when a CronJob run is missed.

    8.2 Podman: run Kubernetes YAML under systemd (Quadlet)

    # /etc/containers/systemd/web-cms.kube
[Unit]
Description=CMS pod (web-server + app server)
After=network-online.target

[Kube]
Yaml=/opt/web/deploy/rendered/cms.yaml
ConfigMap=/opt/web/deploy/rendered/cms-config.yaml
PublishPort=8443:8443
AutoUpdate=disabled        # isolated-network: updates come only through the pipeline

[Service]
Restart=on-failure

[Install]
WantedBy=multi-user.target

    The same cms.yaml is later applied to the cluster. Only the overlay changes.

    8.3 CMS: pod with probes, limits and hardening

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: cms
spec:
  replicas: 1                      # prod overlay patches this to 2 or more
  selector:
    matchLabels: { app: cms }
  template:
    metadata:
      labels: { app: cms }
    spec:
      securityContext:
        runAsNonRoot: true
        fsGroup: 82
      containers:
        - name: app-server
          image: registry.example.internal/web/cms:1.4.2
          envFrom:
            - configMapRef: { name: cms-env }
            - secretRef:    { name: cms-secrets }
          resources:
            requests: { cpu: "500m", memory: 1Gi }
            limits:   { memory: 2Gi }
          securityContext:
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities: { drop: ["ALL"] }
          readinessProbe:
            exec: { command: ["app-server-healthcheck"] }
            periodSeconds: 10
          volumeMounts:
            - { name: files,   mountPath: /app/web/sites/default/files }
            - { name: tmp,     mountPath: /tmp }
        - name: web-server
          image: registry.example.internal/web/web:1.4.2
          ports: [{ containerPort: 8443 }]
          readinessProbe:
            httpGet: { path: /healthz, port: 8443, scheme: HTTPS }
          securityContext:
            readOnlyRootFilesystem: true
      volumes:
        - name: files
          persistentVolumeClaim: { claimName: cms-files }   # RWX on Kubernetes
        - name: tmp
          emptyDir: {}

    apiVersion: batch/v1
kind: CronJob
metadata:
  name: cms-cron

  schedule: "*/15 * * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:

        spec:
          restartPolicy: Never

              envFrom:

                - secretRef:    { name: cms-secrets }
---
apiVersion: batch/v1
kind: Job
metadata:
  name: cms-deploy-1-4-2          # one per release
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: deploy
          image: registry.example.internal/web/cms:1.4.2
          command: ["/bin/sh", "-c"]

    On Podman the same three commands run as a pipeline step before the unit restarts.

    8.5 Search: StatefulSet (the part that really changes)

    apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: search
spec:
  serviceName: search-headless
  replicas: 1                        # staging/prod overlays patch to 2 (matches the sizing baseline)
  selector:
    matchLabels: { app: search }
  template:
    metadata:
      labels: { app: search }
    spec:
      securityContext:
        runAsUser: 8983
        runAsNonRoot: true
        fsGroup: 8983
      containers:
        - name: search
          image: registry.example.internal/web/search:9.x-pinned
          args: ["search", "start", "-f", "-c", "-z", "zk-0.zk-headless:2181"]
          env:
            - { name: SEARCH_HEAP, value: "2g" }          # about half the limit
          resources:
            requests: { cpu: "1", memory: 4Gi }
            limits:   { memory: 4Gi }
          readinessProbe:
            httpGet: { path: /search/admin/info/system, port: 8983 }
          volumeMounts:
            - { name: data, mountPath: /var/search }
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: fast-block
        resources: { requests: { storage: 100Gi } }

    Configset upload as a one-shot Job, so it is repeatable and not a hand step:

    apiVersion: batch/v1
kind: Job
metadata: { name: search-configset-1-4-2 }
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: upload
          image: registry.example.internal/web/search-config:1.4.2   # configset baked in
          command: ["/bin/sh", "-c"]
          args:
            - search zk upconfig -z zk-0.zk-headless:2181 -n web -d /configset &&
              search create_collection -c iss_en -n web -z zk-0.zk-headless:2181 &&
              search create_collection -c iss_fr -n web -z zk-0.zk-headless:2181

    Separate EN and FR collections (or fields) keep per-language index lag measurable.

    8.7 Network rule: only CMS may reach Search

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: search-from-cms-only }
spec:
  podSelector:
    matchLabels: { app: search }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: cms } }

    13. Logical diagrams

    Four views and one footnote. Each figure has a text description, so nothing depends on seeing the picture. The Markdown file carries text versions of the figures.

    Notation: informal boxes and arrows in the style of a C4 container view. Solid arrow: synchronous call or data flow. Dashed arrow: asynchronous. Dashed box: a hosting boundary, or a system outside the platform. NEW and CHANGE tags mark what is different on Kubernetes. Scope: CMS, Search and Analytics, plus what they depend on.

    13.1 Podman stage

    Text description. This is the single-host view used for development and staging. Production on Podman uses two hosts (Figure 7). Users in both official languages reach the reverse proxy cache, which handles TLS with the internal certificate authority. It sends traffic to the CMS pod (web server, app server, queue workers) and the Analytics pod (tracking and reports). CMS talks to Search, which runs in cloud mode with one ZooKeeper, to a Redis cache, and queues video work for the transcode worker. Systemd timers run CMS cron and the Analytics archive job. Search and Analytics use named volumes on the host. Outside the containers, the databases¹ run on dedicated servers, CMS files and backups sit on managed storage, and CMS reaches enterprise systems (identity provider, Mail, records system, Service desk).

    13.2 Kubernetes stage

    Text description. The same three services run inside an on-prem Kubernetes cluster that denies network traffic by default. The ingress controller and the reverse proxy cache receive user traffic. CMS runs as two or more replicas with separate queue workers. Search becomes a two-pod StatefulSet, matching the sizing baseline, with a three-pod ZooKeeper ensemble. Analytics runs as one or two pods. The transcode worker is its own Deployment. Cron and archive work becomes CronJobs, and deploy steps and Search configset upload become Jobs. Storage comes from claims: shared read-write-many for CMS files, block storage for Search and ZooKeeper. The databases¹ stay on their own servers, as do managed storage and enterprise systems. The platform pulls images from the internal registry and gets secrets and certificates from internal services.

    Proxy or Ingress CMS Synchronous HTTPS
    CMS Transcode worker Asynchronous Video jobs via queue
    Proxy or Ingress Analytics Synchronous Tracking requests and report views

    13.3 What maps to what

    Text description. Thirteen things on the Podman side each have a counterpart on Kubernetes. Two are unchanged (the deployment YAML and the reverse proxy cache). Four are new objects that did not exist on Podman. Seven change form. The three marked high effort are shared storage, the Search move to a StatefulSet with ZooKeeper, and backup and restore.

    13.4 Build and carry across into the isolated network

    Text description. Source code is built on the build side from internal mirrors, tested and scanned, then signed with a manifest. The artefact set includes images, deployment definitions, Ansible content, the Search configset and platform images. Security's transfer procedure carries it across. On the isolated side it is imported and verified, pushed to the internal registry, and promoted through development, staging and production without rebuilding. The same artefacts run on Podman now and on Kubernetes later.

    13.5 Footnote 1: databases are not containerized

    Assumed from the project lead's note. Confirm with the database team.

    The CMS and Analytics databases run on dedicated, non-containerized servers owned by the organization. That is the same on Podman and on Kubernetes, so it is the part that does not change. What does change:

    • Firewall allow-list. On Podman the database sees one fixed host address. On Kubernetes, traffic leaves from node addresses or an egress range. Agree a stable range with the database team and Security early.
    • Connection count. More replicas mean more connections. Check the connection limits and use pooling if needed.
    • Network rules. NetworkPolicy allows egress to the database host and port, and nothing else.
    • Encryption and credentials. TLS to the database with the internal CA. Credentials from the isolated network secret store.
    • Backups. Database backup and restore belong to the database team. Test them together with volume backups for CMS files and Search.
    • Rollback. A rollback of the application does not roll back the database. Database updates must work with the previous release for one version, or be paired with a restore.
    • Search rebuild. Rebuilding the Search index from CMS needs the database reachable, so the order of recovery matters.

    15. Sizing: how vCPU and RAM change

    Short answer. The application containers keep the sizes in the solution architecture (section 8). What changes is what surrounds them. On Podman the total is close to the baseline. On Kubernetes it is higher, because of platform overhead on every node, a three-pod ZooKeeper, spare capacity, and a staging environment that has to behave like production.

    Is a full engineering diagram overkill? Yes, at this stage. A diagram of every pod, port, volume and network segment would be the delivery team's design, and this paper sets constraints and outcomes. Two small views are enough: the sizing comparison (Figure 6) and one indicative placement of production on each platform (Figure 7). The delivery team designs the real thing.

    15.1 Starting point

    • The Solution architecture sizes the three environments at 83 vCPU and 230 GB RAM (planning estimate).
    • The databases¹ are on their own servers: 22 vCPU and 80 GB of that total. They do not change between Podman and Kubernetes.
    • That leaves 61 vCPU and 150 GB for the containerized part. Everything below is about that part.
    • The Solution architecture counts instances. Container limits here equal those instance sizes.

    15.2 Assumptions

    Planning estimates. The delivery team validates them in load testing.

    • Production instance counts stay as in the solution architecture: reverse proxy cache 2, CMS 2, Search 2, Redis 1, Analytics 1, transcode worker 1.
    • ZooKeeper is new in both stages (the solution architecture assumed standalone Search). One instance is 1 vCPU and 2 GB. Podman production runs one. Kubernetes production runs three.
    • Each Podman host or Kubernetes worker node reserves 1 vCPU and 2 GB for the operating system, container runtime and agents. The Kubernetes control plane is the organization's shared platform and is not counted.
    • Production on Podman uses two hosts. Production on Kubernetes uses three worker nodes, the minimum for a ZooKeeper quorum.
    • The recommended Kubernetes column adds about 30% spare capacity for rolling updates, rescheduling single pods and bursts. Anti-affinity keeps replicas on different nodes.
    • The recommended Kubernetes staging mirrors production topology (CMS 2, Search 2, ZooKeeper 3). That closes a gap in the solution architecture for the move.

    ZooKeeper 1 instance 3 instances +2 vCPU, +4 GB

    Where Kubernetes can save capacity

    • Transcode worker. On Kubernetes it can request little (for example 2 vCPU and 8 GB) and burst to its limit (8 vCPU and 16 GB) only while encoding. That frees about 6 vCPU and 8 GB of reserved capacity. The cost is slower encoding when the node is busy. Not counted in the numbers above.
    • Shared platform. If the organization's cluster already carries spare capacity, some of the recommended spare capacity is already paid for.

    15.5 Indicative production placement

    Text description. On Podman, two hosts carry production. Each runs a reverse proxy cache, a CMS pod and a Search pod. Host A also runs Redis, ZooKeeper and Analytics. Host B also runs the transcode worker. On Kubernetes, three worker nodes carry the same workloads, plus two more ZooKeeper pods, with a ZooKeeper pod on every node so a quorum survives losing any one node.

    Illustration only. Placement is the scheduler's job on Kubernetes. The figure shows that the workload fits, not where each pod must run.

    15.6 Flags

    • Flag: a two-host Podman production cannot form a safe ZooKeeper quorum. Two hosts can hold one instance, which is a single point of failure for index changes, or three instances where losing one host can still lose the quorum. Options: accept one instance and write the risk down, or add a small third host as a witness. Kubernetes fixes this with three nodes. Verify how Search behaves for reads and writes when ZooKeeper is unavailable, on the pinned version.
    • Flag: the numbers are planning estimates. They come from the solution architecture sizing and the assumptions in 15.2. They are not a delivery team design.
    • Flag: ask IT what overhead its platform really reserves per node. The 1 vCPU and 2 GB figure is an assumption.
    • Flag: network, not servers, is still the real constraint. About 400 Mbps leaves the proxy at 200 viewers. Check the network capacity of the nodes that run the reverse proxy cache.
    • Flag: CPU limits can throttle latency-sensitive pods. Consider requests without hard CPU limits for CMS and the proxy, and test in load testing. Memory limits stay, and Search's heap stays at about half of its memory limit.
