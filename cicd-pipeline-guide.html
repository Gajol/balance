CI/CD Pipeline Guide for a Web Platform

Every code change becomes a tested, secure, accessible and traceable release. One delivery cycle, three separately versioned parts, and gates that stop a bad build.

Contents

    Executive summaries

    For Executives

    CI/CD lowers the risk of every change to the public website. Each release is built the same way, tested automatically, scanned for security and accessibility problems, and traceable back to an approved request. The result: fewer outages, faster fixes for vulnerabilities, and evidence for audit and accessibility compliance.

    • Outcome: safer releases, faster delivery, and an audit trail by default.
    • Investment: time to set up tooling and habits first; savings come from less rework and fewer emergency fixes.
    • Decision needed: agree on the minimum quality gates that no release may skip (see Regression and block-build rules).

    For IT

    The pipeline is one automated path from code to production. It builds a versioned package of CMS code, Search configuration and Analytics settings once, then promotes that same package through test, staging and production. Servers are changed only by the pipeline, not by hand.

    • Build once, deploy many: the same artifact moves through every environment.
    • Config in code: CMS configuration, Search schema and Analytics settings are stored in version control.
    • Rollback: the previous artifact is kept so a bad release can be reversed quickly.
    • Watch it run: logs, metrics and alerts show health after every release.

    For Project Managers

    The pipeline makes progress visible and releases routine. Work is tracked in the work tracker from request to release, and each release records what changed, who approved it and what tests passed. Teams can release smaller changes more often, with less drama.

    • Predictable: smaller releases mean smaller risks and easier planning.
    • Visible: work tickets link to builds, test results and release notes.
    • Gated: a failed check stops the release; no one has to chase it manually.
    • Staged adoption: start with Level 1 and add controls as the team matures (see Maturity stages).

    The pipeline at a glance

    Work moves left to right. A failed gate sends the change back to its author. Only a build that passes every gate reaches production, and what happens there flows back into planning.

    Three layers of validation

    Validation runs from cheapest to most thorough:

    1. On commit: coding standards, static analysis, secret scan, dependency audit. Results in minutes.
    2. On build: unit and functional tests, package and image scan, SBOM creation, signing.
    3. On deploy to test and staging: configuration import and database updates, search checks against known queries, tracking-tag check, browser journeys, accessibility and security scans of the running site.

    Automated checks are not enough

    Automated accessibility tools catch only a portion of real problems. Keep manual testing with assistive technology in the plan for major releases.

    Regression and block-build rules

    Regression testing proves that a new change did not break something that worked yesterday. A block build means the pipeline stops and nothing moves forward until the problem is fixed or a risk acceptance is recorded.

    Gates that can block a build
    GateWhat is checkedBlocks the build whenStart at level
    Code qualityCoding standards, static analysisAny error1
    SecretsPasswords or keys in codeAny finding2
    DependenciesKnown vulnerabilities in CMS, modules and librariesCritical or high severity without an approved exception2
    Functional regressionKey journeys: search, forms, login, content publishingAny failed journey3
    Search regressionA set of known queries returns the expected results from Search; reindex completesExpected results missing or index errors3
    Accessibility regressionAutomated scans compared with the last releaseNew violations on key pages3
    Visual regressionScreenshots compared with the last releaseUnexplained layout change3
    Configuration driftEnvironment matches the configuration in GitDifferences found3
    Telemetry checkAnalytics tag fires and privacy settings are intactTag missing or privacy setting changed3
    Security scan of running siteOWASP ZAP baselineHigh severity finding3

    Start with fewer gates that are always enforced, rather than many gates that people learn to ignore. Every exception needs an owner, a reason and an expiry date recorded in the work tracker.

    Observability and telemetry

    Observability tells the team whether the system is healthy. Telemetry tells the team how people use the site. Both close the loop: what happens in production decides what gets built and fixed next.

    Three habits that make this work

    • Post-release watch: after each release, compare errors and response time with the previous version and roll back if they get worse.
    • Alerts become tickets: every alert that needs action creates a work ticket with an owner.
    • Telemetry feeds the backlog: failed searches and 404s from Analytics become improvement requests.

    Keep personal information out of logs and telemetry, and follow enterprise privacy and retention rules. How these signals reach the enterprise SIEM and NOC is covered on the delivery cycle section above.

    Persona call-outs

    Each role touches the pipeline at different points. The artifacts and gates are the shared language between them.

    IT (platform and operations)

    Owns environments, the artifact repository, deployment and rollback.

    Cares about: signed artifacts, configuration drift checks, Search and Analytics upgrades, monitoring and capacity.

    Works from: runbooks in the wiki and incident and change tickets in the work tracker.

    Developer

    Owns code, tests and fixing failed builds.

    Cares about: fast feedback on commit, clear failure messages, reproducible local builds, Composer lock file and configuration export.

    Works from: work-tracker stories with acceptance criteria; ticket key in every branch and commit.

    Security

    Owns the security gates, exception approvals and vulnerability response.

    Cares about: dependency and image scan results, the component list (SBOM), scan trends, and evidence for assessments.

    Works from: security requirements and risk acceptances recorded in the work tracker and the wiki.

    Product Manager

    Owns what gets built and whether it meets user and accessibility needs.

    Cares about: release notes, accessibility results, Analytics insights, and a predictable release rhythm.

    Works from: the work-tracker backlog, definition of done and release notes in the wiki.

    How the work tracker and the wiki tie it together

    • Work tracker: every change starts as a ticket with acceptance criteria that include security and accessibility. The ticket key links commits, builds and releases, so one view shows status end to end.
    • Wiki: holds the definition of done, gate rules, runbooks, architecture decisions, release notes and risk acceptances.
    • Rule of thumb: if it cannot be traced to a ticket, it does not go to production.

    One pipeline or three?

    Short answer

    Run one delivery cycle with three separately versioned parts. Build and deploy each part on its own. Test all three together every time.

    CMS, Search and Analytics are separate services with their own upgrades and risks. A single build for all three would force a full release for every small change. Three fully separate pipelines would miss the places where the parts depend on each other.

    What the pipeline builds and deploys, by component
    ComponentWhat is builtWhat is deployedCan deploy alone forMust move together when
    CMSPackage of core, contributed modules, custom code and theme (Composer), plus the configuration exportWeb servers; configuration import and database updates run on deployCode, theme and content-type changesSearch fields change (with Search) or the tracking tag changes (with Analytics)
    SearchConfigset: schema, analyzers, synonyms and stop wordsSearch cores or collections; reindex after a schema changeSynonyms, stop words and relevance tuningFields or index structure change (with CMS search configuration)
    AnalyticsApplication version, plus settings kept in Git: sites, goals, privacy settings and the tagAnalytics servers; its own database upgradeVersion upgrades and report changesThe tracking tag or custom events change (with CMS)

    Recommended pattern

    1. One cycle, three build jobs. Each part builds into its own versioned artifact. Jobs start only when that part changes, so a theme edit does not rebuild Search.
    2. One release manifest. A small file lists the exact CMS package, Search configset and Analytics version that were tested together. This file is what moves to staging and production.
    3. Test together, always. The integrated test environment runs the search checks and the tracking check on the whole set, even when only one part changed.
    4. Keep changes reversible. Add the new field or index first, switch over, then remove the old one. Each part can then roll back alone. When a change touches more than one part, a common order is Search, then CMS, then Analytics.

    The delivery cycle

    Each change goes round once. A failed gate at Validate sends the change back to its author. What happens in production feeds the next plan.

    Observability, telemetry and the enterprise SIEM and NOC

    Telemetry is the signals the platform gives off: logs, metrics and usage data. Observability is how the delivery team uses those signals to judge each release. The SIEM and NOC are enterprise services that receive a chosen part of the same signals. They are separate jobs with separate owners, joined by agreed links.

    Same signals, different jobs
    UsePurposeOwnerTypical signalsWhere it goes
    Team observabilityCheck that the site and each release are healthy; decide whether to roll backDelivery team, with DevOpsCMS errors and response time, Search query time and index status, release markersTeam dashboards and alerts
    Usage analyticsLearn how people use the site; feed the backlogProductVisits, searches, failed searches and 404 pages in AnalyticsAnalytics reports only
    Enterprise monitoring (NOC)Keep services available; run incidentsEnterprise operationsUp and down checks, capacity, service health, alert severityEnterprise monitoring and ticketing
    Security monitoring (SIEM)Detect and investigate attacks and misuseSecurity operationsSign-in events, administrator actions, web server and firewall logsEnterprise SIEM

    How they connect

    • Send once, route many. The platform writes standard logs and health checks. An enterprise forwarder sends the right part to the SIEM and the NOC. The team does not build a second pipeline for them.
    • The pipeline deploys the connection. Forwarder settings, health endpoints and alert rules live in Git and are deployed like code.
    • Every deployment leaves a marker. It carries the release number and the work ticket, so a NOC alert or a SIEM finding can be tied to a change record.
    • Agree alert routing early. Decide which alerts page the team, which go to the NOC, and use the enterprise severity names.
    • Keep Analytics data apart. Usage data does not go to the SIEM unless Security asks. Keep personal information out of every log.

    Confirm with Security and the NOC

    Required log fields, retention periods and severity levels differ between organizations. Treat the lists above as a starting point.

    Platform team option

    Short answer

    Align to the DevOps team's platform and tools, then create your own pipeline instance from their shared template. Do not start a new toolchain.

    A platform team already runs and secures the CI/CD service, the runners and the artifact repository. Using them shortens the path to a working pipeline and keeps the web platform inside enterprise support and security approval. The web team adds only what is specific to CMS, Search and Analytics.

    Who provides what with a platform team
    AreaPlatform team providesWeb team adds
    Pipeline serviceCI/CD platform, runners, shared pipeline template, access controlOne pipeline instance for the web platform, with three build jobs
    ArtifactsArtifact repository, signing and retention rulesVersioned CMS package, Search configset, Analytics settings and the release manifest
    Security gatesApproved scanners, secret handling, base policiesCMS-specific checks and the rules for exceptions to block-build gates
    ValidationCommon test and scan stagesRegression journeys, search checks, accessibility checks and the tracking check
    EnvironmentsHosting, on-premises runners, deployment toolingEnvironment settings and deployment steps for each component
    MonitoringLogging and monitoring stack, SIEM and NOC forwardingHealth endpoints, alert rules and release markers, kept in Git

    When to use an instance or a new pipeline

    • Use an instance of the shared pipeline when the template can accept your own stages. This is the usual case and the fastest.
    • Ask for a new template when several teams need the same CMS, Search or Analytics stages. Offer yours back to the platform team so others can reuse it.
    • Request an exception only when a required tool cannot run your checks, for example accessibility scans on a running site. Record the reason and an expiry date.

    With a platform team, the early maturity steps shrink to onboarding onto their template. Most of the web team's effort moves to the CMS, Search and Analytics gates and the regression suite.

    Questions for DevOps and Security

    1. Does the enterprise provide a log forwarder, or do we install one?
    2. Which events must reach the SIEM, and in what format?
    3. Which health checks does the NOC need, and how are they registered?
    4. Can Search and Analytics run on shared platform services, or does the team host them?
    5. Who approves an exception to a block-build gate, and how long does it last?

    Next steps

    A practical path for a team starting out. Finish each step before the next begins.

    1. Weeks 1 to 4 (Level 1): put all code and configuration in version control, pin dependencies with Composer, and create one automated build.
    2. Weeks 5 to 8 (Level 2): add coding standards, dependency and secret scans, and basic accessibility checks; deploy to a test environment automatically.
    3. Weeks 9 to 12 (start Level 3): agree on the block-build rules with Security and the Product Manager, build the first regression journeys (search and key forms), and store signed, versioned artifacts.
    4. After 90 days: add monitoring dashboards and a post-release check, then review the maturity level with the executive sponsor.

    Decisions to confirm

    • Confirm the approved CI tool and artifact repository.
    • Agree the minimum block-build rules.
    • Name an owner for each gate.
    • Define the definition of done in the wiki, including security and accessibility.
