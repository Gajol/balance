Changing the GC Design System for an Intranet: Working Examples

What to keep, what to change and what to add. Click through the examples: identity choices, tight tables, longer French, search that earns trust, hover cards, and engagement patterns a public site never needs.

Contents

    Short answer

    Keep the parts, change the surroundings

    The GC Design System already gives an intranet its forms, accessibility and bilingual behaviour. What an intranet changes is the identity (which public-site elements to keep), the density (how tight the screens are), the delivery (a pinned, self-hosted build) and the missing patterns (search results, directories, dashboards). Make each change in one named place, and write it down.

    Outcome of each example at a glance

    "Change type" tells you how much the design system itself is touched. None of the examples changes the core design system. Every change sits beside it.

    Rule of thumb: wrap, do not fork. Change tokens, never the inside of a component. Anything new goes into a plugin lane with its own prefix.

    The line height and the 65-character reading width stay on prose pages. The variant applies only inside an element that opts in, such as a directory or a table page.
    

    What changes in the design system
    

    Type of change
    Tokens
    

    What is changed
    A few global spacing and type tokens, redefined in one variant stylesheet. The stylesheet applies only to views that opt in, such as directories and tables.
    

    What stays untouched
    Prose pages keep the shipped spacing and reading width. No component internals and no component tokens are touched.
    

    Who
    The design steward owns the stylesheet.
    

    Evidence to keep
    A test with staff, and one line in the override register.

      5. Hover cards: allowed, with conditions
      

      Nothing in the terms of use says no to a hover card. What the terms do say is to avoid deviations, and to base any deviation on user research. So treat a hover card as a plugin component, test it with real users, and check whether the design system already has one before you build.
      

      Try it in the text below. Hover a dotted term, tab to it, press Esc to close it, or move the pointer onto the card. On a touch screen, tap the term.
      

      

      A design token is where a site can express itself. A web component is where it should not. Anything new belongs in a plugin lane, and every deviation goes in the register.
      

      

      What changes in the design system
      

      Type of change
      Plugin
      

      What is changed
      A small "term card" component, and the "preview card" used in search. Both are text-only popups on global tokens. Check the core component list first.
      

      What stays untouched
      All core components. The page text still holds anything essential, so nothing depends on the card.
      

      Who
      The design steward owns the plugin. It is offered upstream.
      

      Evidence to keep
      User research, keyboard and touch tests, a screen reader pass, and a line in the override register.
      

      

      RuleWhat it means for the card
      


      DismissibleEsc closes it without moving the pointer or focus.
      

      HoverableThe pointer can move onto the card without it vanishing.
      

      PersistentIt stays until the user moves away, closes it, or it is no longer valid.
      

      KeyboardFocus shows the same card. Tab order does not change.
      

      TouchTap opens it and a second tap closes it.
      

      No hidden essentialsAnything a person must know is also in the page text or a visible disclosure.
      

      Screen readersThe term points to the card with aria-describedby while it is open. The card holds text only.
      

      FrenchThe card text follows the page language, with room for longer text.
      

      

      


      

      6. Engagement: patterns a public site never needs
      

      A public site speaks to strangers. An intranet speaks to colleagues. That changes who can post, how long posts live, and who looks after them. Two examples show the difference. Neither is a core component, so both are plugins.
      

      

      QuestionPublic siteIntranet
      


      Who posts?Anyone, so you need spam checks.Signed-in staff, so the name is known and no puzzle is needed.
      

      How long does a post live?Until someone removes it.A set time, then it expires on its own.
      

      Who moderates?A central team.A named owner in the business, with a report button for everyone.
      

      What is the risk?Abuse and fraud.Conflict of interest, privacy and tone between colleagues.
      

      LanguageBoth languages for every item.A post may be in one language, with a clear label and the right to ask for the other.

          What changes in the design system
          

          Type of change
          Plugin or organization lane
          

          What is changed
          Two new components: a posting board and a recognition wall. They are built from core form parts (inputs, selects, buttons, error messages) and global tokens. Choose the plugin lane if another organization could use them. Choose the organization lane if the rules are local.
          

          What stays untouched
          Core form components. Core tokens. The rules, expiry and moderation are not design system matters.
          

          Who
          A named business owner for each board. IT owns the component.
          

          Evidence to keep
          The posting rules, retention rule, moderation route and a privacy review, plus a register line for each component.
          Also needed outside the design system: a policy for what may be posted, expiry and reminder jobs, a link to the staff directory, and a reporting route.
          

          Plugin checklist for both: keyboard operable, no colour-only meaning, a visible owner and review date, a moderation route, a retention rule, and labels that fit in French.
          

          


          

          7. Where does a new thing go?
          

          Answer three questions. The result is the lane and the paperwork.
          

          

          1. Does a component in the design system already do this?

          

          2. Could a second organization use it?

          

          3. Does it need to change how a shipped component looks or acts?

          

          Answer all three questions.

          9. Delivery on an isolated network
          

            

          • Build a pinned copy. Install from the package registry on the build side and carry the build across as signed artefacts.
            • 

          • Serve it yourself. No page should fetch styles, scripts or fonts from a public site.
            • 

          • Do not use "latest". Upgrade on your schedule and run the tests first.
            • 

          • Audit external calls. List every address the theme calls, then remove or mirror it.
            • 

          • Treat an external link as content. If a resource lives outside the network, publish a short page about it with an owner and a review date, so it is found and kept fresh.
