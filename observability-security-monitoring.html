Observability and Security Monitoring for a Web Platform

Working paper. Watch from inside. Split at the source. Agree a log contract. Treat silence as a failure.

Contents

    Short answer

    Yes, IaC and CaC are part of this

    The pipeline does not carry the logs. It builds, tests and deploys the settings that do. IaC creates the hosts and containers and the path out of them. CaC sets the log format, the forwarder and the alert rules. Both live in Git, so a log cannot be switched off by accident and the link can be rebuilt on demand.

    Six ideas carry the design.

    1. Watch the site from inside first. The web platform has its own observability platform inside the isolated network. It stores the logs, runs the health checks and shows the team its own dashboards and alerts. The team does not wait for the enterprise to see its own site.
    2. Collect once, split at the source, send one way. One local forwarder feeds that platform. Two export senders then pass two separate streams through a data diode: security events for the SOC-SIEM, and health metrics for the NOC. The NOC stream carries no names, addresses or request paths. A diode cannot filter, so the cleaning happens before data leaves the zone.
    3. Agree a contract. A small file in Git lists the required fields, ports, severity names and owners. Nothing can be sent back across the diode, so the contract is also how the enterprise's needs reach the team: by change request, not by wire.
    4. Treat silence as a failure. A heartbeat event every minute, with a running number on every event, means a quiet link or a missing event raises an alert on the enterprise side.
    5. Show both official languages side by side. A site can be up and still failing in one language. The team platform measures errors, speed and search delay for English and French separately, and treats a gap between them as an alert.
    6. Every alert has a runbook. A runbook is a short page that says what to check and who to call when one alert fires. It lives in Git next to the alert rule.

    Confirmed: data through a diode moves one way

    A data diode is a hardware device that can carry a signal in one direction only. Usually it has a transmit side on one end and a receive side on the other, with no path back. This has four results for the design:

    • No replies. There are no acknowledgements, no handshakes and no requests to resend. TCP and TLS cannot run from end to end across a diode, because both need replies. The usual choices are one-way syslog over UDP, or the diode maker's paired sender and receiver programs that stop and restart the connection on each side.
    • The sender cannot know what arrived. So each event carries a running number. The receiver spots gaps and alerts. The team platform keeps the full copy, and the sender replays on a schedule. The receiver drops repeated numbers.
    • The enterprise cannot reach in. It cannot probe the platform, pull logs, push rules or send test events. The probes run inside the zone. The results go out.
    • Direction is a design choice. This paper assumes the flow is from the isolated platform to the enterprise. Security confirms the direction and the product. A gateway that allows any return traffic is not a diode.

    What goes where

    The same signals serve four jobs. Each job has a different owner and a different destination. The Team column is served by the web observability platform inside the zone. The SOC-SIEM and NOC columns are served through the diode as two separate streams, so only what the contract lists for each stream leaves the zone.

    Two streams leave the zone

    The SOC needs identifying detail to spot an attack. The NOC needs none of it to restore a service. So each gets its own stream with its own list of fields. A diode passes bytes without reading them, so nothing at the boundary can catch a stream that has collected too much. The only control is how the stream is built at the source.

    The two streams and what each one carries
    StreamGoes toCarriesDoes not carry
    Security eventsSOC-SIEMUser ID, source address, session and content identifiers, role and setting changes, outcome. Also the heartbeat and the deploy marker.Page content, record bodies, uploaded files
    Health metricsNOCHost, container and service state, response times, queue depth, search delay for each language, certificate expiry, backup result. Also the heartbeat and the deploy marker.User IDs, source addresses, content identifiers, request paths, search terms, anything personal

    The health stream is built from metrics, not filtered from logs. A request path can identify both a person and a record, so health numbers are never scraped from request logs. The cost is that linking a NOC incident to a SOC event is done by hand, using the time. That is the accepted price of the split.

    Keep personal information out of logs

    The SOC needs a user ID and source address for investigations. It does not need passwords, tokens, form content or search terms. Privacy should confirm which fields are allowed. The NOC stream is stricter still: it carries no personal information at all. The pipeline checks sample logs and sample health events for these items before release.

    How the signals travel

    Each source writes to the host. The local forwarder tags the events, keeps a copy on disk and sends them over an encrypted link to the web observability platform. The platform stores them, runs the health probes from inside the zone and alerts the team. Two export senders take the events each stream lists in the contract, number them and send them once through the data diode: security events in one stream, health metrics in the other. The receiver keeps the streams apart. It passes security events to the SIEM and health metrics to the NOC. Nothing comes back. The pipeline also runs inside the zone and deploys the settings.

    Why code beats hand-built

    • Repeatable. Test, staging and production send logs the same way, so the test proves something about production.
    • Reviewable. A change to what is logged goes through review, and Security can be one of the reviewers.
    • Traceable. Git shows who changed a log setting and when. That answers audit questions.
    • Recoverable. A lost host is rebuilt from Git with the link already in place.
    • Checkable. A daily job compares what runs with what Git says. A difference is drift, and it raises a ticket.

    What healthy means, in both official languages

    A site can be up and still fail one language. A combined number hides it. If the French search index stalls while English keeps moving, the average still looks fine. So the team platform measures each official language on its own and shows the two side by side. Equal service in both languages is an expectation under the Official Languages Act, so it should be proved on a dashboard, not assumed.

    Compare, do not only count

    A gap between English and French on any line above is an alert for the team, not just a chart. Take the numbers from the CMS and the search engine, not from visitor tracking. The analytics tool shows how people use the site. The observability platform shows how the system behaves. Use both and do not mix them.

    Every alert has a runbook

    An alert that wakes someone with no instructions is half an alert. A runbook is a short page for one alert. You may know runbooks as the thick binders of operator steps from older mainframe days. Today they are small pages kept in Git, and some of their steps are automated.

    A runbook is not a runner

    A pipeline runner is the worker program that runs pipeline jobs. A runner can carry out the automated steps of a runbook, such as restarting the forwarder and checking the heartbeat. The runbook is the plan. The runner is one way to do part of it.

    • One runbook per alert. The alert message links to it.
    • It sits in Git beside the alert rule and goes through the same review.
    • It has a named owner and a review date, like any page.
    • Steps are short and in order. Automated steps run through the pipeline, never by hand on production.
    • It ends with who to call and when to escalate.
    • Someone who did not write it follows it in the quarterly drills.

    Example: the heartbeat goes silent

    # runbooks/web-platform-logs-silent.md
Alert:  WebPlatformLogsSilent (no heartbeat for 5 minutes)
Owner:  web team        Reviewed: (date)

1. Look at the team platform. Is the heartbeat still arriving there?
   - Yes: the site is fine. The break is after the platform. Go to step 3.
   - No: go to step 2.
2. Inside the zone, check the forwarder, the platform service, free disk
   space and the host clock.
   - If a logging change was deployed in the last hour, roll it back
     through the pipeline.
3. Check the export senders. Are their running numbers still going up?
4. Ask the diode owner for the diode status. Ask enterprise operations
   whether the receiver is up.
5. Do not open a path back into the zone to look. Nothing flows in.
6. Still silent after 30 minutes: call the web team on-call. If security
   events are silent too, tell Security.

    Common tools

    A tool does one or more jobs. Pick by job, not by brand. The enterprise already runs the SIEM and the NOC, so the web team chooses the first job below, the forwarder, and the tools for its own observability platform inside the zone. The rest helps you talk with Security and Operations and shows what you may meet on their side.

    Short answer on ELK, Beats and Splunk

    ELK is Elasticsearch (store and search), Logstash (parse and route) and Kibana (screens). Add Beats, the light shippers on each host, and it is called the Elastic Stack. Splunk does the same jobs in one commercial product, with a strong search language and a ready-made SIEM add-on. Either can receive what the rsyslog example sends. For the team platform, choose a tool the enterprise already supports, so skills carry over.

    Suggested starting point (to confirm)

    Build one small observability platform for the website inside the zone, from tools the enterprise already supports. It serves the team. Do not copy the SIEM's detection work there: the SOC keeps detection on the enterprise side. On the hosts, use the enterprise-approved forwarder. If there is none, start with rsyslog, as in the examples. For the diode, use the sender and receiver that its owner provides. When the platform moves to Kubernetes, look at Fluent Bit. If traces are added, put the OpenTelemetry Collector in front of whatever the team platform stores them in. Split the export into a security stream and a health stream at the source. Add the per-language dashboard and one runbook per alert from day one. Do not run a second SIEM.

    These show the shape of the code. Host names, ports, paths and metric names are placeholders. The DevOps team, Security and the NOC set the real values and tools.

    1. Repository layout

    IaC and CaC sit in separate folders. The contract and the tests sit beside them.

    platform-repo/
  iac/
    podman/            # Quadlet units, host settings, heartbeat timer
    kubernetes/        # the same services as YAML, used later
  cac/
    forwarder/         # forwarder settings and templates
    cms/config/     # exported CMS configuration
    analytics/            # log section of the Analytics settings
    ansible/roles/     # applies the files above to each host
  contract/
    telemetry-contract.yaml
  monitoring/
    alert-rules/       # heartbeat and health alerts for the NOC
    checks/            # health endpoints to register with the NOC
  runbooks/            # one short page per alert, linked from the alert
  tests/
    log-format/        # sample events and field checks
    drills/            # failure drill scripts
  pipeline/            # stages that extend the shared template

    2. IaC: run CMS under Quadlet with logs to the host journal

    The log driver sends container output to the host journal, where the forwarder picks it up. Search and CMS need no extra log shipping inside the container.

    # iac/podman/web-cms.kube
[Unit]
Description=CMS pod
After=network-online.target rsyslog.service

[Kube]
Yaml=/opt/web/deploy/rendered/cms.yaml
LogDriver=journald
PublishPort=8443:8443

[Service]
Restart=on-failure

[Install]
WantedBy=multi-user.target

    3. IaC: host settings for reliable logging

    # iac/podman/host-logging.yml  (Ansible tasks)
- name: Keep the journal on disk so a reboot loses nothing
  ansible.builtin.copy:
    dest: /etc/systemd/journald.conf.d/persist.conf
    content: |
      [Journal]
      Storage=persistent
      SystemMaxUse=2G

- name: Keep one time source for every host
  ansible.builtin.service: name=chronyd enabled=true state=started

- name: Create the forwarder buffer folder
  ansible.builtin.file:
    path: /var/spool/rsyslog
    state: directory
    owner: root
    group: root
    mode: "0750"

    5. CaC: CMS and Analytics log settings

    CMS's syslog module sends its events to the system log. The settings are exported with the rest of the CMS configuration. Source address and user ID are personal data, so confirm them with Privacy.

    # cac/cms/config/syslog.settings.yml
identity: web-platform-cms
facility: 128
format: '!base_url|!timestamp|!type|!ip|!request_uri|!referer|!uid|!link|!message'

; cac/analytics/config.ini.php  (log section only)
[log]
log_writers[] = file
log_level = WARN
logger_file_path = tmp/logs/analytics.log

    6. CaC: the forwarder settings (inside the zone)

    The forwarder reads the Analytics log file, adds tags, and sends events over TLS to the web observability platform. The disk queue and endless retry protect the data when that platform is down. This link is inside the zone, so replies and retries are fine here.

    # cac/forwarder/50-team-platform.conf
global(
  DefaultNetstreamDriver="gtls"
  DefaultNetstreamDriverCAFile="/etc/pki/web/ca.pem"
  DefaultNetstreamDriverCertFile="/etc/pki/web/forwarder.pem"
  DefaultNetstreamDriverKeyFile="/etc/pki/web/forwarder.key"
)

module(load="imfile")
input(type="imfile" File="/opt/web/analytics/tmp/logs/analytics.log"
      Tag="analytics:" Severity="info" Facility="local1")

template(name="platform" type="string"
  string="<%PRI%>1 %TIMESTAMP:::date-rfc3339% %HOSTNAME% %APP-NAME% %PROCID% %MSGID% - %msg%\n")

if ($syslogfacility-text startswith "local") or
   ($syslogfacility-text == "authpriv") then {
  action(type="omfwd" target="platform.example.internal" port="6514"
    protocol="tcp" template="platform"
    StreamDriver="gtls" StreamDriverMode="1"
    StreamDriverAuthMode="x509/name"
    StreamDriverPermittedPeers="platform.example.internal"
    queue.type="LinkedList" queue.filename="fwd_platform"
    queue.spoolDirectory="/var/spool/rsyslog"
    queue.maxDiskSpace="2g" queue.saveOnShutdown="on"
    action.resumeRetryCount="-1" action.resumeInterval="10")
}

    7. CaC: the one-way export (two streams to the diode)

    The platform writes each stream to its own file: security events in one, health metrics in the other. A sender reads each file, adds a running number that belongs to that stream and sends each event once over UDP to the diode. The health file is written from metrics and never holds a forbidden field. There is no queue to retry and no TLS here, because the diode cannot carry replies. Keep each event short, so it fits in one datagram. Illustration only: confirm the protocol and the number scheme with the diode owner.

    # cac/export/60-diode-export.conf
module(load="imfile")
module(load="mmsequence")

template(name="numbered" type="string"
  string="<%PRI%>1 %TIMESTAMP:::date-rfc3339% %HOSTNAME% %APP-NAME% %PROCID% %MSGID% [web@32473 stream=\"%$!stream%\" seq=\"%$!seq%\"] %msg%\n")

# Stream 1: security events, for the SOC-SIEM
input(type="imfile" File="/var/export/security.log"
      Tag="export-security:" Severity="info" Facility="local2"
      Ruleset="send_security")
ruleset(name="send_security") {
  set $!stream = "security";
  action(type="mmsequence" mode="instance" from="1" to="2000000000" var="$!seq")
  action(type="omfwd" target="diode-sender-sec.example.internal" port="514"
    protocol="udp" template="numbered")
}

# Stream 2: health metrics, for the NOC. No personal field is ever written here.
input(type="imfile" File="/var/export/health.log"
      Tag="export-health:" Severity="info" Facility="local3"
      Ruleset="send_health")
ruleset(name="send_health") {
  set $!stream = "health";
  action(type="mmsequence" mode="instance" from="1" to="2000000000" var="$!seq")
  action(type="omfwd" target="diode-sender-health.example.internal" port="514"
    protocol="udp" template="numbered")
}

    8. CaC: apply the forwarder settings with Ansible

    The role keeps a backup of the old file, checks the full configuration and only then restarts the forwarder.

    # cac/ansible/roles/forwarder/tasks/main.yml
- name: Install the forwarder settings from Git
  ansible.builtin.template:
    src: 50-team-platform.conf.j2
    dest: /etc/rsyslog.d/50-team-platform.conf
    owner: root
    group: root
    mode: "0640"
    backup: true
  notify: restart rsyslog

- name: Check the whole configuration before any restart
  ansible.builtin.command: rsyslogd -N1
  changed_when: false

- name: Record the release for the drift check
  ansible.builtin.copy:
    content: "{{ release_id }}\n"
    dest: /etc/web/forwarder.version

    9. The telemetry contract

    This file is the agreement. The pipeline tests against it. The SOC and NOC review changes to it. Because nothing can be sent back across the diode, this file is also how the enterprise's needs reach the team.

    # contract/telemetry-contract.yaml
version: 2
transport:
  inside_zone:
    platform: platform.example.internal
    port: 6514
    protocol: syslog over TLS
  export:
    direction: out only, through the data diode
    protocol: syslog over UDP        # confirm with the diode owner
    acknowledgements: none
    numbering: running number per stream, in structured data
    replay_every_minutes: 60
    receiver_drops_repeats: true
  clock: UTC from the enterprise time source

streams:
  security:
    sender: diode-sender-sec.example.internal
    to: SOC-SIEM
    priority: [security_events, heartbeat, deploy_marker, major_errors]
    required_fields: [timestamp, host, app, severity, user_id, source_ip, request_id, release]
    events:
      - cms.login_success
      - cms.login_failure
      - cms.role_change
      - cms.admin_action
      - web.access
      - os.auth
    gap_alert: { after_missing: 1, routed_to: SOC }
  health:
    sender: diode-sender-health.example.internal
    to: NOC
    kind: metrics and state only, never log lines
    priority: [heartbeat, deploy_marker, service_state, search_delay_per_language]
    required_fields: [timestamp, host, service, language, metric, value, release]
    forbidden_fields: [user_id, source_ip, request_id, request_path, search_terms, content_id]
    metrics:
      - service_up
      - response_time_seconds
      - queue_depth
      - search_index_delay_seconds     # one value per language
      - certificate_days_left
      - backup_last_success
    gap_alert: { after_missing: 1, routed_to: NOC }

severity_names: [info, minor, major, critical]   # use the enterprise names
heartbeat:
  interval_seconds: 60
  in_streams: [security, health]
  silence_alert_after_seconds: 300
  routed_to: NOC
deploy_marker:
  fields: [release, work_ticket, approved_by, time]
alerts:
  every_alert_has: [runbook, owner]
inbound_changes: by change request only; nothing flows back through the diode
owners:
  forwarder: web-team
  team_platform: web-team
  export_senders: web-team
  platform_administration: role to be named before go-live
  diode: to be named by Security
  receiver_and_collector: enterprise-operations
  siem_rules: security-operations

    10. Pipeline: the gates that protect the link

    The first job blocks a build when the test event does not arrive at the team platform or in both export queues, when the health stream carries a forbidden field, or when an alert has no runbook. The second checks that the platform is talking again after a deploy. Both checks run inside the zone. The enterprise side confirms receipt by ticket.

    # pipeline/telemetry.yml  (generic CI syntax)
verify-telemetry:
  stage: validate
  script:
    - ansible-lint cac/ansible iac/podman
    - tests/log-format/check.sh contract/telemetry-contract.yaml tests/log-format/samples/
    - tests/send-test-event.sh --target team-platform-test --release "$RELEASE_ID"
    - tests/expect-arrival.sh --target team-platform-test --release "$RELEASE_ID" --timeout 120
    - tests/expect-in-export-queue.sh --stream security --release "$RELEASE_ID" --timeout 120
    - tests/expect-in-export-queue.sh --stream health --release "$RELEASE_ID" --timeout 120
    - tests/check-health-stream.sh contract/telemetry-contract.yaml tests/log-format/samples-health/
    - tests/every-alert-has-runbook.sh monitoring/alert-rules/ runbooks/
  allow_failure: false

announce-deploy:
  stage: deploy
  script:
    - tools/send-deploy-marker.sh --release "$RELEASE_ID" --ticket "$WORK_TICKET"
    - tools/expect-heartbeat.sh --source team-platform --host "$TARGET_HOST" --release "$RELEASE_ID" --timeout 300

    11. CaC: the NOC alerts for silence and gaps (enterprise side)

    These rules live on the enterprise side. The team cannot deploy them across the diode, so they are agreed in the contract and requested by change request. The team platform has its own, similar rules for the team. The SOC keeps a matching rule for gaps in the security stream on its side.

    # monitoring/alert-rules/heartbeat.yaml  (example format)
groups:
  - name: web-platform-telemetry
    rules:
      - alert: WebPlatformLogsSilent
        expr: time() - web_heartbeat_last_seen_timestamp_seconds > 300
        for: 2m
        labels:
          severity: major      # use the enterprise severity name
          route: noc
        annotations:
          summary: "No heartbeat from the web platform for 5 minutes"
          runbook: "runbooks/web-platform-logs-silent.md"

      - alert: WebPlatformEventsMissing
        expr: increase(web_export_sequence_gaps_total{stream="health"}[15m]) > 0
        labels:
          severity: minor      # use the enterprise severity name
          route: noc
        annotations:
          summary: "Numbers are missing from the health stream: data was lost between the sender and the receiver"
          runbook: "runbooks/web-platform-events-missing.md"

    Proving it works

    A link that is never tested will fail when it is needed. These checks make the proof routine.

    Checks that show the SOC-SIEM and NOC link works
    CheckWhenPasses when
    Test eventEvery build, in the test environmentThe event reaches the team platform within two minutes with all required fields, and shows in the export queue.
    Heartbeat after deployEvery deployThe heartbeat with the new release number shows on the team platform within five minutes, and the NOC sees it after the next export.
    Detection testEach release that changes logging, and every quarterA burst of failed sign-ins in test raises a SIEM alert on the enterprise side, through the test diode path.
    Platform failure drillEvery quarter, in testWith the team platform cut for an hour, the forwarder buffer fills and then empties after reconnection. No gap appears in the platform.
    Diode failure drillEvery quarter, in testWith the receiver switched off for an hour, the NOC silence alert fires. After it returns, the replay fills the gap and repeats are dropped.
    One-way checkEvery year, with SecurityEvery attempt to connect from the enterprise side back into the zone through the diode path fails.
    Health stream content checkEvery buildA scan of sample health events finds none of the forbidden fields. A planted test field makes the check fail, which proves the check works.
    Language gap drillEvery quarter, in testWith the French search queue paused for an hour, the French search delay alert fires while the combined number stays quiet.
    Runbook drillEvery quarterSomeone who did not write the runbook picks one alert at random and resolves it using only that page. Gaps are fixed in Git.
    Drift checkDailyRunning settings match Git. A difference opens a ticket.
    Certificate checkDailyNo forwarder certificate expires within 30 days.

    Where the tests run. Build-time checks run before release, on the build side: log format, forbidden fields, runbook links and a test event to a test platform. The path across the real diode can only be proved inside the isolated network, so plan time there for the first end-to-end test.

    Questions for Security and the NOC

    1. Which receiver address, port and protocol does the diode use? Is a paired diode path available?
    2. Which fields and event names must every log line carry? Who approves changes to that list?
    3. Which fields may include personal information, and which are forbidden?
    4. How long must logs be kept, and where? Does the local disk buffer count?
    5. Who writes the SIEM parsing and detection rules for CMS, Search and Analytics events?
    6. Nothing can be sent back, so how does the NOC register health checks and alert rules? Is a change request the route, and who confirms it?
    7. Which severity names does the enterprise use, and which severities page a person?
    8. Is there a test diode path, or another way to confirm that test events arrived on the enterprise side?
    9. Who owns the diode? Does it run from the zone to the enterprise? How fast can it carry data, and what status signal does it give?
    10. Which protocols does the diode accept: UDP syslog, files or its own proxy programs? Can it carry running numbers?
    11. Which metrics does the NOC want, and in what format? Can it take numbers rather than log lines?
    12. Which role is named to run the platform day to day: patching, upkeep, on-call and runbooks? It must be named before go-live.
    13. Who may read the team platform's logs, and who may change or delete them? How is that shown to auditors?
    14. Where do build-side tests run, and what stands in for the diode there? When can the first end-to-end test inside the isolated network happen?
