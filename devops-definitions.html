    Delivery and pipelines

    How a change moves from a request to production.

    CI/CD

    Continuous Integration and Continuous Delivery

    What it means
    A way of working where every change is built, tested and prepared for release automatically. Continuous Integration merges and tests small changes often. Continuous Delivery keeps the result ready to deploy at any time.
    Why it matters
    Small, frequent, tested changes are safer than large, rare ones. Fewer surprises reach production, and fixes arrive faster.
    Keys to success
    • Keep changes small and merge them often
    • Automate the build and the tests, not just some of them
    • Treat a broken build as the team's first priority
    Read more: CI/CD Pipeline Guide

    Pipeline

    The automated path a change follows

    What it means
    The ordered set of automated steps that takes code from a commit to a running system. Typical stages are build, test, scan, package and deploy.
    Why it matters
    The same path runs every time, so results are repeatable and every release leaves a record. It also shows exactly where a change failed.
    Keys to success
    • Build once and promote the same package through each environment
    • Keep the pipeline definition in version control
    • Make every run visible to the whole team
    Read more: Delivery cycle

    Gate

    A rule that can stop a build

    What it means
    A check in the pipeline that must pass before the change moves on. Examples are failed tests, a known vulnerability, or a missing approval.
    Why it matters
    Gates turn policy into something that runs every time. Security and quality rules apply to every change, not only the ones someone remembers to review.
    Keys to success
    • Start with a few clear gates and add more as trust grows
    • Give a clear message when a gate fails and say how to fix it
    • Review exceptions on purpose and record them
    Read more: CI/CD Pipeline Guide

    Maturity level

    How far a team has taken its automation

    What it means
    A simple scale that describes how developed a team's delivery practice is, from mostly manual steps to fully automated and measured.
    Why it matters
    It lets teams agree on where they are and what the next step is. It also keeps goals realistic, because nobody jumps to the top level in one move.
    Keys to success
    • Assess honestly and name one next step
    • Improve one level at a time
    • Measure results such as lead time and failed releases
    Read more: CI/CD Pipeline Guide

    Rollback

    Returning to the last working version

    What it means
    Putting the previous, known-good release back in place when a new release causes a problem.
    Why it matters
    It limits the damage of a bad release. A fast, tested way back lets teams release with less fear.
    Keys to success
    • Keep the previous release package available
    • Practise the rollback before you need it
    • Plan for data changes, because code can go back but data may not
    Read more: Delivery cycle

    Platform and containers

    What runs, and how it is packaged, deployed and described.

    CMS, Search and Analytics

    The three parts of the web platform

    What it means
    CMS manages and publishes the web content. Search provides search. Analytics measures how the site is used.
    Why it matters
    The three parts depend on each other and are released together. A shared delivery cycle keeps their versions compatible.
    Keys to success
    • Agree on one delivery cycle for the three parts
    • Test the connections between them, not only each part alone
    • Name one owner for each part
    Read more: Delivery cycle

    Container

    A packaged application and what it needs to run

    What it means
    A sealed package that holds an application and its libraries. It runs the same way on a laptop, in test and in production.
    Why it matters
    It removes the problem of software working in one place and not another. It also makes patching a matter of replacing a package, not repairing a server.
    Keys to success
    • Build images from approved, scanned base images
    • Run as a non-root user with limited resources
    • Keep data outside the container
    Read more: Podman to Kubernetes

    Podman

    A tool for running containers

    What it means
    A container engine that runs containers without a central background service. It can run as an ordinary user and works well with systemd.
    Why it matters
    It is the planned starting point for the platform. It is simple to operate on a server and does not need a cluster.
    Keys to success
    • Run containers rootless where possible
    • Use Kubernetes YAML so the later move stays small
    • Keep host patching on a regular schedule
    Read more: Podman to Kubernetes

    Quadlet

    Container units managed by systemd

    What it means
    A way to describe a container or a Kubernetes YAML file in a small unit file. Systemd then starts it, restarts it and logs it like any other service.
    Why it matters
    It gives containers the same start, stop and restart behaviour as the rest of the server. Operations teams already know how to run it.
    Keys to success
    • Use the .kube unit type to run the Kubernetes YAML
    • Deploy the unit files with Ansible
    • Test a restart after every change
    Read more: Podman to Kubernetes

    Kubernetes

    A platform that runs and manages many containers

    What it means
    A system that schedules containers across servers, restarts them when they fail, scales them and connects them through a network.
    Why it matters
    It is the planned later stage. It offers more automatic recovery and scaling, but it also adds new skills, new security work and new cost.
    Keys to success
    • Plan the move from the start, so it is a move and not a rebuild
    • Set network rules to deny traffic by default
    • Confirm storage and backup before the first workload
    Read more: Podman to Kubernetes

    IaC

    Infrastructure as Code

    What it means
    Describing servers, networks and platform settings in files that are stored, reviewed and run by tools, instead of being set up by hand.
    Why it matters
    Environments can be rebuilt the same way each time. Every change has an author and a record, which supports audit and recovery.
    Keys to success
    • Store all definitions in version control
    • Review changes like application code
    • Run the same code in every environment
    Read more: Podman to Kubernetes

    CaC

    Configuration as Code

    What it means
    Describing application and system settings in files, such as the CMS configuration, the Search configset or an Ansible playbook, so they are applied automatically.
    Why it matters
    It removes hand-edited settings that nobody can explain later. Drift between environments is found and corrected.
    Keys to success
    • Keep secrets out of the files and use the secret store
    • Apply configuration through the pipeline, not by hand
    • Check for drift on a schedule
    Read more: Podman to Kubernetes

    Isolated network

    A network with no connection to the internet

    What it means
    A secure network that is physically or logically separated from the internet. Software and updates cross only through a controlled transfer.
    Why it matters
    It protects sensitive systems, but it changes how teams build and update software. Nothing can be pulled from the internet at deploy time.
    Keys to success
    • Build outside, sign the package, then carry it across
    • Use internal mirrors for libraries and images
    • Turn off update checks and other calls to the outside
    Read more: Podman to Kubernetes

    Mirror

    An internal copy of outside software sources

    What it means
    A copy of public libraries, packages and container images, held inside the secure network and kept up to date by a controlled process.
    Why it matters
    Inside an isolated network, builds and installs cannot reach the internet. The mirror is where they get what they need.
    Keys to success
    • Name an owner and a refresh schedule
    • Scan what comes in before it is added
    • Pin exact versions so builds repeat
    Read more: Podman to Kubernetes

    Artefact signing

    Proving who built a package and that it has not changed

    What it means
    Adding a digital signature and a checksum to each image, file and deployment definition. The receiving side checks both before it uses them.
    Why it matters
    It lets the secure side trust what crossed the isolated network. Anyone assessing the system can trace a running container back to its source commit.
    Keys to success
    • Sign at build time, in the pipeline
    • Verify on import and again before deploy
    • Protect the signing keys and record who can use them
    Read more: Podman to Kubernetes

    Drift

    When a running system no longer matches its code

    What it means
    The gap that appears when someone changes a server or a setting by hand, so it differs from what the IaC and CaC files say.
    Why it matters
    Drift causes surprises, hides security gaps and makes a rebuild unreliable. It often explains a problem that shows up in only one environment.
    Keys to success
    • Make changes through the pipeline only
    • Compare running systems to the code on a schedule
    • When you find drift, fix the system or update the code, and record the decision
    Read more: Podman to Kubernetes

    Monitoring and security

    How the platform tells the enterprise how it is doing.

    Observability

    Being able to tell what a system is doing from what it reports

    What it means
    Collecting logs, events and health signals from the platform so a team can see what is happening and find the cause of a problem.
    Why it matters
    Problems are found before users report them, and the cause is found faster. Security and operations teams get the same facts.
    Keys to success
    • Decide what each signal is for before collecting it
    • Use consistent log formats and timestamps
    • Test the signal path as part of the pipeline
    Read more: Observability and security monitoring

    SIEM and SOC

    Security Information and Event Management, and the Security Operations Centre

    What it means
    The SIEM is the tool that collects and correlates security logs. The SOC is the team that watches it, investigates alerts and responds.
    Why it matters
    Attacks are often seen first as a pattern across many logs. The platform must send the right events, or the SOC cannot see a problem.
    Keys to success
    • Agree with the SOC on which events to send
    • Include user, time, source and result in each event
    • Plan how logs are kept if the link goes down
    Read more: Observability and security monitoring

    NOC

    Network Operations Centre

    What it means
    The team that watches the health of services and networks and responds to outages.
    Why it matters
    It sees availability and performance problems around the clock. It needs clear alerts to act quickly.
    Keys to success
    • Send alerts that say what is wrong and who owns it
    • Keep alert noise low so real issues stand out
    • Write a short runbook for each alert
    Read more: Observability and security monitoring
